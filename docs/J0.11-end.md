# J0.11 — Instruction END, Locomotive BASIC 1.1 CPC 6128

**État : En revue Pilotage.** Ne pas fusionner. Ne pas commencer J0.12.

## Objet et périmètre

Implémentation native C99 sans Z80 de END dans le sous-ensemble déjà
livré : tokenizer, listing, exécuteur et CLI hôte. Les modules
basic_program, basic_session, basic_executor et basic_session_runtime
conservent leurs interfaces et signatures publiques. Pas d'allocation
dynamique ni de périphérique dans core/.

## Sources historiques et confiance

Source : http://cpctech.cpc-live.com/docs/basic.asm (Locomotive BASIC 1.1).

- **[C] E663 :** dans le groupe des mots commençant par E,
  le désassemblage contient « defb "N","D"+&80,&98 ».
  Le token de END est donc **0x98**.
- **[C] Table de dispatch :** « defw cc31 ;; END ».
- **[C] CC31–CC35 :** la routine END se compose de « ret nz »,
  « call cc66 », « jr cc5a ». La voie CC5A ferme les flux
  CLOSEIN / CLOSEOUT et rejoint la console. STOP (CC26–CC2F)
  dispose d'un traitement distinct incluant le message « Break ».
- **[D]** En exécution native, END arrête le programme sans imprimer
  de texte propre ; les instructions ultérieures ne sont pas atteintes.
  Les instructions qui l'ont précédée restent acquises.
- **[V]** Tester sur CPC 6128 / ROM réelle 1.1 les variantes
  syntaxiques plus larges et le comportement éventuel de CONT,
  des fichiers et du message Ready après END.
- **[B]** Absence de capture binaire indépendante de la RAM CPC.
  Ces vecteurs sont déduits du désassemblage et non obtenus par
  une capture directe sur la machine historique.

## Choix de réalisation

1. Le tokenizer reconnaît END sans distinction de casse, sur les
   mêmes frontières lexicales que les autres instructions. END
   produit le token 0x98, sans argument ; les séparateurs
   explicites restent encodés par 0x01.
2. REM et apostrophe conservent leur queue opaque. Une occurrence
   de END dans une chaîne PRINT reste un littéral.
3. Le listing reconstruit 0x98 en END en préservant les espaces
   et les colons autorisés ; les allers-retours sont testés.
4. L'exécution de END vérifie la terminaison ou le séparateur
   du statement atteint, sans interpréter le suffixe inatteignable.
   L'instruction déplace le curseur vers la sentinelle finale,
   à l'offset program.size - 2, et retourne BE_OK.
5. Le même appel à be_step traite au maximum une ligne. Les sorties
   des PRINT précédant END sur cette ligne et le curseur sont
   commités de manière atomique après la passe de validation ;
   une erreur de capacité ne modifie rien. Le be_step suivant
   renvoie BE_END sans mutation. Le runtime retourne alors
   BSR_END et passe à BSR_IDLE. **Cette convention de pilotage
   hôte ne reproduit pas le timing de la console CPC.**
6. GOTO rencontré avant END sur une même ligne provoque un
   changement de ligne qui contourne END. Une commande directe
   END reste non supportée dans la console actuelle.

## Matrice de vérification

La neuvième suite CTest, « termination », couvre :

- token CPC 0x98, variantes de casse, frontières, espaces, colons,
  allers-retours tokenizer / listing, END dans une chaîne,
  dans REM ou après apostrophe ;
- sortie « AVANT » avant END et absence de « INTERDIT » ;
- PRINT "A":END:PRINT "B", END:PRINT "INVISIBLE",
  END seul, END avec espaces, GOTO avant END ;
- BE_OK sur la ligne atteignant END, curseur sentinelle,
  BE_END à l'appel suivant, état BSR_IDLE et reprise LIST / RUN ;
- absence de mutation après BT_NO_SPACE, BL_NO_SPACE,
  BE_NO_SPACE et BE_BAD_SEQUENCE ; rejet d'une ligne
  tokenisée malformée et correction après erreur.

La suite « host_cli » comporte trois nouveaux scénarios de
bout en bout. Le total attendu est **9/9 suites CTest**
en Linux standard et en ASan/UBSan sur le dernier HEAD.
