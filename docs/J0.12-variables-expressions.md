# J0.12 — Variables scalaires et expressions du véritable Locomotive BASIC 1.1

**État : En revue Pilotage — étude uniquement, aucune API implémentée.**  
**Référence : Amstrad CPC 6128, Locomotive BASIC 1.1.** Portage C99 *natif* prévu sur ESP32-2432S028R (sans Z80, sans PSRAM). Ce document ne revendique **pas** la compatibilité complète du moteur actuel : J0.1–J0.11 n'implémentent pas encore les variables ni les expressions.

## 1. Variables : syntaxe, identité et stockage

### 1.1 Identifiants et type effectif

| Propriété | Constat historique / preuve | Décision native envisagée |
|---|---|---|
| Début de nom | **[C]** FF92 (classe « lettre »), E03A–E070 (analyse lexicale), D65A–D67E (lettres de DEF). **[D/TECH]** Commence par une lettre A–Z, pas un chiffre. | Valider le premier octet comme lettre CPC, **pas** via \`isalpha\` dépendant de locale. |
| Suite du nom | **[C]** E075–E0A4 appelle FF9C (lettre/chiffre/point) ; E097 copie les caractères du nom. **[D/TECH]** A–Z, 0–9, point \`.\` ; pas de \`_\` générique. | Analyse lexicalement bornée de l'intégralité du nom. |
| Longueur | **[C]** D991–D9A4 réserve jusqu'à 40 octets et déclenche une erreur lorsque B tombe à zéro. **[D]** 40 caractères significatifs, à vérifier aux limites exactes [V]. | Maximum *provisoire* de 40 octets CPC ; ne pas tronquer silencieusement. |
| Casse | **[C]** E03F/FFAB normalise les mots-clés ; D99D–D9A4 applique \`AND DF\` pendant la construction de nom pour la résolution. **[D]** Identité insensible à la casse ; LIST conserve éventuellement la graphie source. | Canonicaliser en ASCII majuscule **dans la clé**, conserver les octets de programme pour LIST. |
| Suffixes explicites | **[C]** E0D1–E0E1 et E07C–E08B : \`%\` → token de variable entière \`02\`, \`$\` → chaîne \`03\`, \`!\` → réel \`04\` ; suffixe consommé par le tokeniseur. | Associer \`%\` à INT16, \`$\` à STRING, \`!\` à REAL5. |
| Nom sans suffixe | **[C]** E081–E08B et D96C–D990 : famille \`0B/0C/0D\` avec résolution du type implicite selon la table DEF, pouvant réécrire un marqueur. | Résoudre le type **selon l'état d'exécution**, sans réécrire le flux persistant canonique. |
| Type par défaut | **[C]** D638–D64F initialise A–Z au type réel taille 5 ; D650, D654, D658 choisissent respectivement STRING (3), INT (2), REAL (5). | Tableau \`default_type[26]\` initialisé à REAL. |
| DEFINT / DEFREAL / DEFSTR | **[C]** D65A–D67D : listes de lettres/ranges \`A-Z\` inclusifs ; D63D écrit un type par initiale. **[V]** Répercussions sur variables déjà résolues, références tokenisées déjà mises en cache. | Une mutation d'état runtime ; aucune hypothèse de retypage rétroactif sans test. |
| Identité / collisions | **[C]** D740–D764 compare successivement *tous* les octets de nom jusqu'au bit 7 final, et code de type (masque \`07\`) ; D96C–D9C8 résout les types implicites. **[D]** \`A%\` distinct de \`A!\` ; \`A\` peut être alias de \`A!\` lorsqu'il est typé REAL. \`ABC\` et \`ABD\` ne doivent pas fusionner sur leurs premiers caractères. | Clé = **(nom complet normalisé, type résolu)**, pas (premières lettres, suffixe brut). |
| Lecture avant affectation | **[D]** D6C9–D709 et D717–D7DF recherchent/créent des entrées en mémoire de variables ; D791–D795 les initialise à zéro. **[V]** Rendu exact de chaîne vide et effets d'une simple lecture. | Préparer INT=0, REAL=0, STRING vide ; démontrer chaque cas par oracle avant validation complète. |

**Attention [B] :** la résolution implicite est *temporelle*. Une référence \`A\` compilée/tokenisée avant \`DEFINT A-Z\`, une référence atteinte après la directive et une référence déjà mise en cache ne peuvent pas être assimilées sans examen de D96C–D990 et test différentiel. Ne pas coder une règle « DEFINT retype toutes les variables existantes » par commodité.

### 1.2 Représentation des références tokenisées

**[C, ROM E070–E0A8 ; D931–D946 ; D96C–D9C8]** : forme pertinente des références ordinaires dans le corps d'une ligne, **hors** en-tête d'enregistrement J0.2 :

\`\`\`text
[type: 1 octet] [cache/offset: 2 octets LE, initialement 00 00]
[nom: N octets, bit 7 positionné sur le dernier octet]
\`\`\`

Familles observées : \`02\` INT explicite \`%\`, \`03\` STRING explicite \`$\`, \`04\` REAL explicite \`!\` ; \`0B/0C/0D\` sans suffixe et/ou après résolution. **[C]** D931 lit les deux octets d'offset puis saute le nom en recherchant le bit 7. D96C convertit le nom et peut déterminer un type implicite. D740–D764 contrôle nom et type. **[V]** Il faut mesurer sur des lignes tokenisées 6128 quels variantes exactes \`0B/0C/0D\` apparaissent à chaque phase et la signification définitive des offsets selon l'état ROM : ne pas annoncer une adresse CPC absolue, un offset hôte, ou un identifiant de variable stable dans le fichier.

**Proposition [architecture]** : conserver **les deux octets de cache CPC dans l'image de programme**, zéro dans les nouvelles références persistantes, **sans jamais** y écrire un pointeur ESP32. Créer au besoin un cache de résolution *distinct*, indexé par \`(generation_programme, offset_token, generation_variables, generation_DEF)\`, invalidé à chaque mutation pertinente. Pour import/export CPC, préserver les octets canoniques et définir explicitement la politique des images éventuellement mutées par RUN. J0.2 applique déjà le principe analogue à \`1E/1D\` pour les lignes.

### 1.3 Organisation historique — ne pas la confondre avec C

| Élément ROM | Preuve | Conséquence et réserve |
|---|---|---|
| Zone variables | **[C]** D5F0 : \`AE68\` début variables/DEF FN ; D5F3 : \`AE6A\` début tableaux ; D5F6 : \`AE6C\` première zone libre. | Zones contiguës déplacées/agrandies historiquement ; **pas** de pointeurs de zone CPC dans le cœur C99. |
| Recherche/enregistrement | **[C]** D717–D7DF, D740–D7A7 ; listes et comparaison bit 7 ; tailles de valeur liées aux types 2, 3, 5. | **[D]** Organisation liée/relative ; layout exact par entrée/overheads **non fixé** pour le C. |
| Réel / entier / chaîne | **[C]** D638/D650/D654/D658 utilise 5/3/2 comme tailles ; FB58–FB89 lit un descripteur chaîne de 3 octets : longueur \`u8\`, adresse \`u16\`. | La représentation C peut utiliser des offsets plus larges et est **distincte** de l'image CPC. |
| Chaînes et littéraux | **[C]** FB4D–FB78 recopie dans la zone chaînes des données initialement référencées depuis le programme si nécessaire ; FB8A–FB94, FBD3–FC41 gèrent pile et durées de vie ; \`B071/B073\` bornes de zone chaînes. | **[B]** Durée de vie, alias, libération/compactage et erreurs mémoire exactes demandent un jalon spécifique. |
| Pile d'exécution | **[C]** F672/F662 (réservation/dépilement de cadres), CF62–CFC3 (évaluation), B06F (prochain sommet). | Séparer en C pile d'évaluation typée, appels FOR/GOSUB et mémoire chaînes temporaires. |

### 1.4 Valeurs initiales et affectation

- **[D]** Avant une première écriture, une variable scalaire numérique est initialisée à zéro par création en mémoire (D791–D795) ; la chaîne vide a un descripteur de longueur zéro. Un test indépendant \`PRINT X%:PRINT X!:PRINT X$\` reste **[V]**, notamment pour le format de sortie.
- **[C]** LET implicite/explicite converge vers D68E ; D69F–D6B3 effectue comparaison/conversion des types, puis stockage. **[D]** Une affectation est une opération *typée* : \`A%=...\` doit valider conversion/range, jamais troncation silencieuse C.
- **[V]** La création d'une variable pendant une tentative d'évaluation qui échoue et l'ordre de ses effets internes ne sont pas couverts par les contrats J0.7.

## 2. Nombres : représentation CPC et chemin numérique

| Catégorie | Format CPC (stockage/flux) | Constat et contrainte native |
|---|---|---|
| Entier | **[D/TECH]** signé 16 bits en mémoire, domaine \`-32768..32767\`, deux octets ; représentation arithmétique interne ROM dans HL/DE. | Utiliser \`int16_t\` pour la **valeur validée**, \`int32_t\`/\`uint32_t\` pour vérifier les bornes avant conversion. Ne jamais laisser le débordement signé C décider. |
| Réel | **[C/D, TECH + FLOAT]** 5 octets : octets 0..2 = partie basse de mantisse, octet 3 = bit 7 signe + 7 bits hauts de mantisse, octet 4 = exposant biaisé ; bit haut de mantisse implicite. | Stocker **cinq octets bruts CPC**, sans les intercaler dans un \`float\` ou \`double\` non contractuel. |
| Chaîne | **[C]** descripteur ROM longueur 8 bits + adresse 16 bits ; données octetaires ; jusqu'à 255 octets **[D/TECH]**. | En natif : \`(arena_offset, length)\`, octets, aucune présomption UTF-8/NUL final. |
| Booléen / relation | **[C]** D013–D01A puis FF2D produit un entier issu de la comparaison ; convention CPC \`-1\` vrai et \`0\` faux **[D]**. | Représenter comme INT16, pas \`bool\` C visible par BASIC. |

**[D, FLOAT/TECH]** Décodage mathématique d'un réel 5 octets \`b0..b4\` pour \`b4 != 0\` :

\`\`\`text
sign = (b3 & 0x80) ? -1 : +1
fraction32 = 0x80000000 | ((b3 & 0x7F)<<24) | (b2<<16) | (b1<<8) | b0
valeur = sign * (fraction32 / 2^32) * 2^(b4 - 128)
\`\`\`

\`b4=0\` est l'encodage usuel de zéro (mantisse non significative) **[D/TECH]**. Un bit de signe + **31 bits fractionnaires stockés** donnent **32 bits significatifs** au total, mais **ni** les arrondis intermédiaires **ni** les règles d'affichage décimal ne sont déduits de cette seule structure. L'article FLOAT illustre \`PI\` avec \`A2 DA 0F 49 82\` ; c'est un **exemple documentaire externe**, pas un vecteur mesuré ici. **[B]** Reproduire l'arithmétique des ROMs firmware Maths Pack et la conversion décimale avant d'affirmer l'identité de \`PRINT 1/3\`.

**[C]** Le BASIC supérieur délègue à la ROM firmware : addition \`BD7C\`, soustraction \`BD82\`, multiplication \`BD85\`, division \`BD88\`, comparaison \`BD8E\`, conversions \`BD67/BD6A/BD6D\` (voir FD0C–FD67 et FDD5–FEFB). **La ROM BASIC seule ne prouve donc pas l'arrondi de la division**, l'étendue exacte des nombres, les sous-flux ou la règle des décimales affichées.

### 2.1 Littéraux et leurs tokens

**[C] E0E2–E150 ; D092–D0CE ; E32F–E39D ; EA34–EA44** :

| Forme | Token | Charge utile | Notes |
|---|---|---|---|
| Constantes 0..9 | \`0E..17\` | aucune | **[C]** reconnaissance immédiate |
| Valeur 10 | chemin E114–E123 | **[C]** \`19 0A\` dans la tokenisation étudiée | **[V]** la table générique \`18\` existe au décodage, mais E116 branche avant de l'émettre pour 10 |
| Entier décimal 8 bits | \`19\` | \`u8\` | **[C]** |
| Entier décimal 16 bits | \`1A\` | \`u16 LE\` | **[C]** ; interprétation signé/non signé selon contexte à tester aux bornes **[V]** |
| Binaire | \`1B\` | \`u16 LE\` | **[C]** pour préfixe \`&X\` |
| Hexadécimal | \`1C\` | \`u16 LE\` | **[C]** pour \`&H\` ou \`&\` |
| Référence de ligne | \`1E\` | \`u16 LE\` | **[C]** distinct de la constante numérique générale \`1A\` |
| Référence de ligne optimisée | \`1D\` | \`u16\` lié à une adresse CPC | **[C]** E920–E941 ; traitement hôte différé J0.2 |
| Réel | \`1F\` | **5 octets CPC** | **[C]** E393/EA3F, ne pas réinterpréter en IEEE |
| Signe \`-\` / \`+\` | \`F5\` / \`F4\` | pas inclus dans les bits d'un littéral positif | **[C]** tokenisation de signe et opérateurs ; prise en compte par l'analyseur |

**[C]** E0FA appelle la conversion du texte numérique (ED8A) ; suivant le type obtenu, E103 choisit \`1F\` ou E107–E123 une forme entière. **[V]** Décimales, exposants \`E\`/\`E+\`/\`E-\`, \`&X\`/\`&H\`, nombre \`32768\`, signe et erreurs de conversion exigent des captures binaires indépendantes. Notamment, **la représentation d'un littéral 32768 ne signifie pas** qu'une variable entière peut contenir 32768.

### 2.2 Conversions et débordements

- **[C]** FD0C–FD47 : \`+\`, \`-\`, \`*\` essayent l'opération entière avec test de débordement ; si nécessaire, convertissent les opérandes en REAL puis utilisent le firmware flottant. **[D]** Débordement d'une **opération** entière et débordement d'une **affectation** vers \`A%\` ne sont pas le même scénario.
- **[C]** FD52–FD67 : \`/\` appelle le firmware REAL, même pour des entrées entières ; \`\\\` et \`MOD\` passent par des conversions en entier ; FD61/FD83 chemin de division par zéro.
- **[C]** FDB4–FEFB : \`CINT\`, \`CREAL\`, \`FIX\`, \`INT\` et conversions/rejets sont spécifiques. **[V]** Mode d'arrondi (en particulier moitié, négatifs, frontières), valeur nominale des débordements et différences par opcode doivent être relevés par cas. Un cast C \`(int16_t)real\` est interdit comme implémentation de la règle CPC.
- **[B]** Ordre exact des arrondis et des erreurs du Maths Pack non couvert par la seule ROM BASIC ; prévoir un modèle numérique déterministe CPC5 + tests d'oracle. \`double\` peut servir **uniquement de comparateur auxiliaire de test**, jamais de preuve de compatibilité.

## 3. Expressions : priorités, types, associativité

### 3.1 Grammaire/algorithme déduits de la ROM

**[C]** CF62 démarre une expression avec \`B=00\` ; CF6D/CF73–CFC3 sélectionnent l'opérateur et appellent récursivement l'évaluation du membre droit. D033 analyse un opérande primaire (variable, valeur, \`"..." \`, fonction, parenthèses) ; D059 est la table des préfixes ; D0D1 lit les parenthèses. La table **CFED**, reconstituée par instructions et **[B80 ExprEvaluator.asm]**, fournit la priorité suivante (valeur la plus élevée = plus forte liaison) :

| Niveau ROM hex | Opérateurs / construction | Sources | État |
|---:|---|---|---|
| \`16\` (22) | \`^\` | CFED+12, CFA4–CFA8 | **[C/D]** |
| \`14\` (20) | \`-\` unaire ; \`+\` unaire = préfixe sans calcul | D01D–D027, D036 | **[C]** |
| \`12\` (18) | \`*\`, \`/\` | CFED | **[C/D]** |
| \`10\` (16) | \`\\\` division entière | CFED, FD67 | **[C/D]** |
| \`0E\` (14) | \`MOD\` | CFED, FD79 | **[C/D]** |
| \`0C\` (12) | \`+\`, \`-\` binaires ; \`+\` sur chaînes = concaténation | CFED, CF80–CF95, FD0C/FD21 | **[C/D]** |
| \`0A\` (10) | \`>\`, \`=\`, \`>=\`, \`<\`, \`<>\`, \`<=\` | CFC5–CFEB, D00B–D01A | **[C]** |
| \`08\` (8) | \`NOT\` (préfixe) | D028–D032 | **[C]** |
| \`06\` (6) | \`AND\` | CFED, FD87 | **[C]** |
| \`04\` (4) | \`OR\` | CFED, FD92 | **[C]** |
| \`02\` (2) | \`XOR\` | CFED, FD9C | **[C]** |
| primaire | Parenthèses, littéral, référence de variable, fonctions | D033–D0D1/D0DA | **[C]** |

**[C]** CFA5–CFA8 compare la priorité courante à celle du prochain opérateur et **retourne aussi en cas d'égalité**. **[D]** Le même opérateur de niveau égal est donc évalué **de gauche à droite**, y compris \`^\`. En conséquence, \`2^3^2\` donne *candidat ROM statique* \`(2^3)^2=64\`, et \`-2^2\` donne *candidat* \`-(2^2)=-4\`. **[V]** Contrôler ces sorties réellement sur CPC 6128 (et les parenthèses explicites de contrôle), car aucune capture n'est jointe.

**[C]** CF80–CF95 : \`+\` détecte une valeur chaîne, évalue le second terme et appelle F91D (concaténation). **[V]** Coercitions, chaînes temporaires, comparaisons de chaînes, erreurs si type mixte et ordre d'évaluation nécessitent des tests : **ne pas supposer** que l'opérateur \`+\` sur chaînes est numérique ou que \`PRINT\` insère automatiquement des conversions.

**[C]** D013–D01A et FD49/FDA6 : opérateurs de relation/bit à bit renvoient/emploient des entiers CPC ; \`NOT\` est un complément binaire sur entier signé et non un NOT booléen C. **[D]** Vrai = \`-1\`, faux = \`0\`. **[V]** Vérifier la conversion des réels en opérandes logiques et les bornes.

**[D]** L'algorithme de référence se traduit naturellement par un parseur de précédence / Pratt, avec **table explicite ROM** et limite de profondeur, sans Z80, sans interprétation par \`eval\`, sans AST alloué par expression. **[B]** Préciser et tester les effets de bord/lazy evaluation (ex. fonctions système, appels \`FN\`) avant de déclarer l'ordre d'évaluation totalement fidèle.

### 3.2 Erreurs CPC vs diagnostics internes

| Situation | Code/chemin CPC | Proposition C99 |
|---|---|---|
| Syntaxe incorrecte | **[C]** \`02\` = Syntax error : CB49/CB55 | \`EXPR_SYNTAX\`, position token |
| Opérande manquant | **[C]** D055 appelle CB45 avec \`16\` hex (22 décimal) | \`EXPR_MISSING_OPERAND\` |
| Argument invalide | **[C]** \`05\` = Improper argument : CB4D | \`EXPR_ARGUMENT\` |
| Débordement | **[C]** \`06\` = Overflow : FD1E/FDFB | \`EXPR_OVERFLOW\` |
| Épuisement mémoire | **[C]** \`07\` = Memory full : F875, CB55 | \`EXPR_CAPACITY\` + mappage contextualisé |
| Division par zéro | **[C]** \`0B\` hex (11 déc.) : FD83/CB45 | \`EXPR_DIV_ZERO\` |
| Incompatibilité de type | **[C]** \`0D\` hex (13 déc.) : message CE0B | \`EXPR_TYPE_MISMATCH\` |
| Mémoire de chaînes | **[C]** \`0E\` (14), \`0F\` (15), \`10\` (16) : CE14–CE29 | \`EXPR_STRING_SPACE\` / \`EXPR_STRING_TOO_LONG\` / \`EXPR_TOO_COMPLEX\` |
| Plafond interne natif | **[architecture]** aucune équivalence générale CPC prouvée | \`EXPR_LIMIT\` **distinct** d'une erreur ROM |
| Token tronqué, image invalide | **[architecture]** validation défensive native | \`EXPR_TRUNCATED\`/\`EXPR_BAD_PROGRAM\`, non numéros ROM inventés |

**[V]** La correspondance « situation exacte → erreur CPC et ordre d'apparition » doit être testée. Les erreurs \`BP_*\`, \`BT_*\`, \`BE_*\` ne sont **pas** des codes CPC. **[B]** Une erreur d'allocation native ne justifie pas automatiquement le message ROM Memory full, notamment lorsqu'une limite artificielle de profondeur est atteinte.

## 4. Matrice de conformité ciblée (hypothèses non présentées comme observations)

Les lignes suivantes sont **des cas indépendants ou un scénario séquentiel à différencier**. Le jeu complet de 12 lignes dans un même \`RUN\` modifie les types par \`DEFINT\` à la ligne 80 : aucune lecture rétrospective de la ligne 10 ne doit être présumée. Capturer à la fois les sorties, erreurs/numéros, \`LIST\` et octets tokenisés **avant et après RUN**.

| Ligne / fragment | Comportement attendu ou déduction | Références ROM ; token/encodage | Preuve / test |
|---|---|---|---|
| 10 \`A=1\` | \`A\` implicitement REAL au démarrage ; affectation de 1. | D638–D64F, D68E–D6B3, D96C–D990 ; variable sans suffixe famille \`0B..0D\`, 1 token \`0F\` | **[D/V]** identité et cache à inspecter |
| 20 \`LET A%=5\` | \`A%\` INT, distinct de \`A\` si celle-ci est REAL. | LET \`A5\`, \`A%\` \`02 00 00\` + nom marqué, 5 token \`13\` ; D740/D75A | **[C/D]**, dump à produire [V] |
| 30 \`PRINT A%\` | Valeur attendue \`5\` avec formatage PRINT CPC, **pas** celui du CLI provisoire. | PRINT \`BF\`, variable \`02\`; D6C9, CF62 | **[D/V]** sortie et espaces exacts |
| 40 \`A$="CPC"\` | Chaîne scalaire, trois caractères ; stockage via descripteur. | \`03 00 00\` + nom, guillemets \`22\` ; FB58–FB89 | **[C/D]**, mémoire/durée de vie [V] |
| 50 \`PRINT (1+2)*3\` | Expression arithmétique, résultat numérique attendu \`9\`. | parenthèses D0D1, \`+\` \`F4\`, \`*\` \`F6\`, constantes \`0F 10 11\` | **[D]**, sortie CPC [V] |
| 60 \`PRINT -2^2\` | Candidat \`-4\` : \`^\` priorité 22 > moins unaire 20. | D01D, CFED \`16\`, puissance \`F8\`, moins \`F5\` | **[D/V]** confirmer sortie CPC |
| 70 \`PRINT 2^3^2\` | Candidat \`64\` : égalité de précédence → retour CF A8, association gauche. | CFA5–CFA8, \`F8\` | **[D/V]** différentiel majeur |
| 80 \`DEFINT A-Z\` | Table de types implicites A..Z = INTEGER à partir de l'exécution de la directive. | \`8E\`, D654–D67D, ADF3..AE0C (26 entrées), déduit de D638–D64F / D97C–D983 | **[C]** effet futur ; variable déjà résolue **[V/B]** |
| 90 \`A!=1.5\` | Type REAL explicite, valeur non entière 1,5 ; possible même variable logique que \`A\` REAL de ligne 10. | \`04 00 00\` + nom, littéral réel \`1F\` + 5 octets CPC, E103–E150 | **[D/V]** dump réel/alias |
| 100 \`PRINT 1/3\` | Division REAL ; valeur décimale et arrondi affiché **non déclarés**. | \`F7\`, FD52–FD64 → firmware \`BD88\` | **[C]** chemin, résultat exact **[B/V]** |
| 110 \`A%=32767\` | Borne INT maximale admissible. | \`02\` + nom ; littéral \`1A\` attendu si conversion entière conservée, E103–E150 | **[D/V]** format littéral & stockage |
| 120 \`A%=32768\` | Dépasse la plage INT ; échec attendu à la conversion/affectation, code \`06\` *probable* à confirmer. | D69F, FEEB–FEFB, CB55 ; \`1A\` ou \`1F\` selon conversion | **[D/V/B]** code et traitement exact à mesurer |

**Protocole de référence [V]** : sur **CPC 6128 BASIC 1.1** réel ou environnement de référence documenté, partir d'un \`NEW\`/\`CLEAR\`, saisir chaque ligne, noter \`LIST\`, générer un dump binaire des enregistrements, lancer \`RUN\`, relever chaque \`PRINT\` et erreur avec numéro, puis redumper si possible (caches mutables). En tests **isolés**, séparer \`A=1:A!=2\`, \`A=1:A%=2\`, \`DEFINT A-Z:A=1.5\`, \`A=1:DEFINT A-Z:PRINT A\`, \`PRINT -2^2\`, \`PRINT 2^3^2\`, \`PRINT (2^3)^2\`, \`PRINT 2^(3^2)\`, \`A%=32767\`, \`A%=32768\`, \`PRINT 1/3\`, et variantes de chaînes ; ne pas présenter les propres vecteurs statiques comme une référence de comportement CPC indépendante.

**Règles d'intégration :**

1. **Évaluer le flux binaire**, pas une re-tokenisation ad hoc du \`LIST\`. Toujours parser les charges \`02..0D\`, \`19..1F\`, \`FF xx\`, guillemets et séparateurs dans leurs bornes ; aucune lecture à travers \`body_length\`. Le parseur devra consommer les opérandes et retourner **un offset d'arrêt**, pour laisser à l'exécuteur ses séparateurs (\`:\`, \`THEN\`, virgule, etc.) selon le contexte.
2. **Séparer les types et l'arithmétique** : INTEGER exact vérifié, REAL5 avec encode/decode et opérations déterministes inspirées du Maths Pack, conversions configurées par règle CPC, formatage décimal CPC distinct du calcul. La substitution \`float\`/IEEE 754 est proscrite par défaut.
3. **Résolution de variable** : lire le nom complet, décoder suffixe/type implicitement selon la table DEF au moment historique approprié, chercher \`(nom,type)\`, ne jamais exposer la disposition mémoire de la ROM aux clients. Invalidation à mutation du programme/type/variables ; pas de pointeur natif écrit dans les tokens.
4. **Arènes appelant** : pas de \`malloc/free\` internes, bornes de noms 40, chaînes 255, nombre de variables configurable, profondeur d'expression et nombre de temporaires bornés. Une erreur de capacité doit être déterministe et ne jamais devenir un buffer overflow.
5. **Contrat J0.7 préservé** : pendant J0.12 aucun code touché ; lors d'une future intégration, \`be_step\` ne doit valider/publier \`cursor\`, sortie et \`*written\` qu'après validation totale de la ligne. Toute allocation/écriture de variable ou effet de fonction \`RND\` pendant cette phase demande soit **journalisation + commit** soit une **redéfinition documentée et acceptée** de l'atomicité pour les effets BASIC historiques. **[B]** Le modèle de snapshot/rollback de tous effets latéraux ne découle pas de la ROM. Ne jamais prétendre que le contrat actuel est déjà satisfait par \`bexpr_eval\`.
6. **Ports Linux/ESP32** : pas de locale C, pas de dépendance aux tailles de pointeurs, pas de lecture de \`uint16_t\` par cast depuis un flux (\`u16 LE\` explicite), ni unions sérialisées ; détection d'alias par plages validées si \`uintptr_t\` disponible comme dans J0.7. Taille totale contrôlée **avant** écriture.
7. **Tests** : fuzz de flux tronqués, erreurs d'offset, noms maximaux, chaînes zéro/255, profondeur excessive ; différentiel CPC pour conversion, priorité, erreurs, affectation et \`PRINT\`. Les tests Linux internes ne constituent jamais seuls une validation de fidélité CPC.

### 5.3 Budget mémoire prévisionnel ESP32 (hypothèses, **pas mesures**)

Exemple **configurable à l'initialisation**, indépendamment du heap/stack FreeRTOS et des buffers LCD. Unité : **KiB = 1024 octets**.

| Poste de travail | Hypothèse de dimensionnement | Prévision |
|---|---|---:|
| \`BasicProgram\` (zone utile, déjà existante) | Arène lignes 24 KiB, sentinelle incluse | 24 KiB |
| Enregistrements scalaires | 192 cases × **24 octets majorants provisoires** (à remplacer par \`sizeof\` réel) | 4,5 KiB |
| Noms canoniques | Arène 8 KiB ; max 40 octets/nom + bookkeeping | 8 KiB |
| Chaînes persistantes et temporaires | Arène 12 KiB, compacte, maximum d'objets borné | 12 KiB |
| Workspace expression | 32 cadres × **24 octets majorants provisoires**, et états temporaires fixes | 0,75 KiB |
| Scratch parsing / conversions | 2 KiB, sans tampon d'écran | 2 KiB |
| **Total arènes ci-dessus** | Hypothèses sans overhead systémique ni alignement additionnel | **51,25 KiB** |

Cette estimation **ne prouve ni capacité totale du CYD ni tenue en charge**. L'ESP32 classique partage ses SRAM avec les piles des tâches, Wi-Fi, pilotes et TFT, sans PSRAM ; il ne faut pas confondre 520 Ko SRAM annoncés et heap contigu disponible. Il faut mesurer \`heap_caps_get_free_size\`/\`largest_free_block\`, marges de piles FreeRTOS, tailles de structures compilées, heap minimal durant les tests, marge LCD/SPI et fragmentation ; interdire une grosse allocation TFT 320×240×2 octets par défaut. Configurer l'arène depuis un bloc statique ou mémoire du système **à taille vérifiée**, pas dix \`malloc\` opportunistes. Si la limite d'allocation échoue, renvoyer une erreur explicite et ne rien corrompre.

## 7. Incréments d'implémentation suggérés **à partir de J0.13** (non commencés)

1. **J0.13 proposé — lexèmes/références variables et validation documentaire** : compléter **spécification/test** du flux \`02..0D\` et identité des noms ; code éventuel de **décodage borné sans mutation**, le reste inchangé.
2. **J0.14 proposé — valeurs typées et stockage scalaire** : descripteurs appelant + noms/collisions + DEF tableau et initialisation ; sans expression générale, tests unitaires et atomiques.
3. **J0.15 proposé — réels CPC5 bas niveau** : pack/unpack et tests de référence ; conversion/arrondis séparés par incréments, aucune arithmétique \`float\` substitutive.
4. **J0.16 proposé — évaluateur arithmétique borné** : parenthèses/constantes/variables, précédences et statut d'erreur, sans fonctions à effets latéraux.
5. **J0.17+ proposés — logique, relations, chaînes et intégration PRINT/LET** : incréments autonomes, validation différentielle et intégration transactionnelle avec le moteur existant ; autres commandes ensuite.

Ce planning est **une proposition**, pas un engagement de livraison ni une autorisation de commencer J0.13. **J0.12 se termine uniquement par une revue Pilotage** des preuves, de l'architecture, du budget RAM et des inconnues historiques. Les **9/9 suites Linux et 9/9 ASan/UBSan** du dernier jalon sur \`main\` sont la référence de non-régression ; la CI propre à cette PR doit être vérifiée séparément.
