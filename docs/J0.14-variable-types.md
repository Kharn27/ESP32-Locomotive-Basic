# J0.14 — Types implicites et clés scalaires canoniques

**État : Accepté par Pilotage et fusionné sur `main` via [PR #14](https://github.com/Kharn27/ESP32-Locomotive-Basic/pull/14), squash `9f5a7bac5ba776e25e9e497e40b34e093c028b48`.** CI [#40093559178](https://github.com/Kharn27/ESP32-Locomotive-Basic/actions/runs/40093559178) : 11/11 Linux, 11/11 ASan/UBSan ; revue déposée en commentaire GitHub. Réimplémentation native C99 indépendante du matériel pour **Locomotive BASIC 1.1 de l'Amstrad CPC 6128**. Les tests sont **synthétiques** ; aucun n'est une capture ni une preuve expérimentale sur CPC réel.

## 1. Fondements historiques et niveaux de preuve

- **[C] ROM BASIC 1.1 D638–D64F** : initialisation de 26 entrées à partir de `BC=415A` (A–Z), avec `E=05`, dans la table à `ADB2` ; valeur REAL par défaut.
- **[C] D650–D65A** : `DEFSTR` sélectionne `03`, `DEFINT` sélectionne `02`, `DEFREAL` sélectionne `05`. **D65A–D67D** analyse les lettres, plages inclusives et listes de directives ; les plages inversées mènent à une erreur de syntaxe ROM.
- **[C] D96C–D990** : pour certaines références (marqueur `>=0B`), la ROM lit l'initiale et consulte la table A–Z ; cette procédure peut modifier le marqueur en mémoire, selon le type.
- **[C] D991–D9A4** : copie du nom avec limite historique 40 caractères ; **D9AF–D9C8** : traitement des familles de marqueurs avant sélection du type runtime.
- **[C] E075–E0A8, E1B5–E1BA** (étudiés en J0.13) : séquence marqueur, cache deux octets, nom à bit 7 final. **[V]** Sens exact de `0B/0C/0D` suivant les étapes de résolution et modification des caches : validation indépendante encore nécessaire.

Les types de la table sont **des codes de type runtime**, non les octets de marqueur : la référence explicite REAL utilise le marqueur `04` dans J0.13 mais la table DEF contient `05` pour REAL. Les marqueurs optimisés `0B/0C/0D` ne sont jamais interprétés en types par ce module.

## 2. Formats publics, taille et possession

En-tête `core/basic_variable_types.h` :

| Structure / type | Champs exacts | Taille / invariant |
|---|---|---|
| `BasicVariableType` | `BVT_INTEGER=02`, `BVT_STRING=03`, `BVT_REAL=05` | Énumération de codes logiques ; stockage interne en `uint8_t` |
| `BasicVariableTypes` | `uint8_t types[26]` | 26 octets ; une entrée par lettre A..Z |
| `BasicVariableName` | `uint8_t length; uint8_t bytes[40]` | 41 octets ; longueur 1..40 ; lettres majuscules ASCII, chiffres et points ; suffixe inutilisé à zéro |
| `BasicVariableKey` | `uint8_t type; uint8_t name_length; uint8_t name[40]` | 42 octets ; type effectif + nom canonique complet |

Les trois structures sont **possédées par l'appelant**, ne contiennent aucun pointeur et n'allouent rien. Les tailles sont assurées par l'usage de tableaux d'octets ; elles sont contrôlées dans les tests. On ne compare **jamais une énumération C par représentation binaire brute**. L'identité de deux clés est l'égalité du type effectif, de `name_length`, puis de tous les `name_length` octets. Les octets restants sont initialisés à zéro par construction pour éviter tout contenu indéterminé.

## 3. API, capacité et atomicité

```c
BVTStatus bvt_init(BasicVariableTypes *table);
BVTStatus bvt_get_implicit(const BasicVariableTypes *table, char initial,
                           BasicVariableType *out_type);
BVTStatus bvt_set_range(BasicVariableTypes *table, char first, char last,
                         BasicVariableType type);
BVTStatus bvt_canonicalize(const uint8_t *source, size_t source_length,
                            size_t offset, BasicVariableName *out_name);
BVTStatus bvt_build_key(const BasicVariableName *name,
                         BasicVariableType effective_type,
                         BasicVariableKey *out_key);
```

- `bvt_init` met chaque entrée à REAL (05) ; `bvt_set_range` écrit la plage **inclusive** validée, sans analyser ni exécuter l'instruction DEF de BASIC. Une modification ultérieure écrase seulement les lettres ciblées.
- `bvt_get_implicit` accepte `A..Z` et `a..z`, utilise leur indice normalisé ; refuse une valeur interne de table non reconnue. Il ne modifie pas la table.
- `bvt_canonicalize` **appelle `bvr_decode` J0.13** pour valider la référence ; `source_length` est la longueur réellement accessible ; `offset` doit être strictement inférieur à cette longueur. À partir de `name_offset` et `name_length`, elle copie les 1..40 caractères, masque le bit 7 terminal, convertit uniquement `a..z` en `A..Z` et conserve chiffres/points. Son résultat ne dépend plus de la durée de vie du programme tokenisé. Aucun cache CPC n'est traduit en adresse hôte. La longueur utile est conservée (pas de troncature à 8 caractères).
- `bvt_build_key` exige un `effective_type` **fourni explicitement** et valide, ainsi qu'un nom déjà canonique ; elle refuse longueur invalide, minuscules, caractères non autorisés et queue non nulle. Le champ `type` est copié tel quel, sans interprétation du marqueur. Cette fonction n'évalue aucune directive DEF ni aucun programme.
- Chaque fonction valide les arguments et les bornes **avant d'écrire l'état ou la sortie**. En cas d'échec, aucune mutation du tableau, des résultats ni de la source ; les fonctions de lecture refusent le chevauchement de l'entrée et de la destination via `uintptr_t` et soustraction (contrat Linux/ESP32 hérité de J0.13). Aucun `malloc`, état global mutable, float/double, Arduino, ESP-IDF ou Z80.

Statuts internes (non assimilables aux erreurs affichées par la ROM CPC) : `BVT_OK`, `BVT_INVALID_ARGUMENT` (pointeur NULL ou offset initial hors limites), `BVT_INVALID_LETTER` (hors alphabet ASCII), `BVT_INVALID_RANGE` (première lettre après dernière), `BVT_INVALID_TYPE`, `BVT_INVALID_NAME`, `BVT_INVALID_REFERENCE` (erreur du lecteur J0.13, qui peut être interrogé directement pour son statut précis), `BVT_OVERLAPPING_MEMORY`. Des pointeurs invalides et des tailles mensongères sont hors contrat C ; seules des zones mémoire effectivement accessibles peuvent être fournies.

## 4. Typage et clé

**Type explicite** : déduit d'un suffixe BASIC `%`, `!` ou `$` déjà codé dans une référence de famille `BVR_FAMILY_EXPLICIT`, mais **sans le résoudre automatiquement dans J0.14**. **Type implicite** : valeur de la table de la lettre initiale au moment où la résolution est demandée ; par défaut REAL. **Type résolu/effectif** : choix fait par un futur résolveur à partir du contexte historique, d'un éventuel suffixe et de la table ; **entrée obligatoire de `bvt_build_key`**.

Les exemples `A%`, `A!`, `A$` sont représentés par un même nom canonique `A` et trois clés différentes : `(A,INTEGER)`, `(A,REAL)`, `(A,STRING)`. `A.B` n'est jamais égal à `AB` ; les lettres au-delà du huitième octet et jusqu'à la 40e sont conservées. Les chiffres et les points ne sont pas retirés. La casse est normalisée car l'analyse ROM des initiales est insensible à la casse ; cette normalisation ne prétend pas reproduire toutes les règles de nommage CPC non encore étudiées.

## 5. Tests et limites

`tests/test_basic_variable_types.c` forme la **11e suite CTest** ; couvre la valeur par défaut de 26 lettres, les plages inclusives et recouvrantes, la casse, les erreurs atomiques, les références tronquées/corrompues, `SIZE_MAX`, le chevauchement des buffers, les noms d'un caractère et jusqu'à 40, les points et chiffres, les collisions de préfixe et de noms très longs, ainsi que trois identités typées. La source tokenisée ne change pas. Validation standard et ASan/UBSan sont exécutées par la CI de PR sur les onze suites ; les résultats doivent être constatés sur le commit final, pas présumés.

**[V] À confirmer sur CPC indépendant** : encodage réel des noms et cas lexicaux limites ; timing et rétroactivité de `DEFINT/DEFREAL/DEFSTR` en présence de variables déjà résolues ; réécriture des marqueurs optimisés `0B/0C/0D` et cache avant/après RUN ; interaction des types avec l'aliasing et les erreurs CPC. **[B]** Aucun stockage de valeurs, exécution de DEF*, environnement d'expressions ou intégration à RUN. Ces fondations ne prouvent donc **pas** encore la compatibilité complète avec les programmes CPC 6128.
