# J0.23 — Audit mémoire et faisabilité anticipée ESP32 CYD

**Statut : livré, en revue Pilotage.** Référence de départ : `main` @ `7d5f90031bb02a729f1687081d251bffb3ca44d0` (J0.22 + documentation). Aucune modification du cœur portable ni de la sémantique BASIC.

## 1. Portée, preuves et reproductibilité

L'outil `tools/basic_memory_budget.c` est un exécutable **C99** qui inclut **les vrais en-têtes** de `core/`. Il évalue `sizeof` et l'alignement C99 (via `offsetof`) et reconstitue quatre budgets « caller-owned ». Son test CTest vérifie la cohérence structurelle et l'absence de débordement arithmétique dans les scénarios, **sans assertions de taille ABI prédéterminées**. Ce programme ne mesure **ni la pile d'exécution**, ni une allocation de heap réellement réalisée.

Vérification locale de l'outillage au moment de l'audit documentaire (25 octobre 2026) : GCC `14.2.0` Debian, CMake `3.31.6` ; `idf.py` et `xtensa-esp32-elf-gcc` introuvables dans le `PATH`. La compilation **cible ESP32 n'a pas eu lieu**. Les valeurs hôte effectivement obtenues devront porter la version du compilateur et l'ABI du runner ; elles ne se transfèrent pas automatiquement à Xtensa.

Reproduction Linux, avec et sans instrumentations :

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug -DBP_SANITIZERS=OFF \
  -DCMAKE_C_FLAGS=-fstack-usage
cmake --build build --parallel
ctest --test-dir build --output-on-failure
./build/basic_memory_budget
cc --version
cmake --version
size --version
size -A build/loco_basic_cli
find build -name '*.su' -type f -print

cmake -S . -B build-asan -DCMAKE_BUILD_TYPE=Debug -DBP_SANITIZERS=ON \
  -DCMAKE_C_FLAGS=-fstack-usage

ctest --test-dir build-asan --output-on-failure
./build-asan/basic_memory_budget
```

Le workflow GitHub `.github/workflows/basic-program.yml` effectue les tests Linux normaux et ASan/UBSan, exécute le rapport ABI, imprime les sections de la CLI et un extrait des estimations de pile. Le premier run [GitHub Actions #40192584687](https://github.com/Kharn27/ESP32-Locomotive-Basic/actions/runs/40192584687), sur le HEAD `132b2ff85c6b8eb8ebc49eca9940ba7c3136ec1e`, établit **20/20 tests Linux et 20/20 ASan/UBSan**, ainsi que les tableaux de mesure présentés ci-dessous ; le run final de la PR sera vérifié en revue. La CI reste la preuve de test automatique à examiner pendant la revue ; **un résultat vert ne prouve pas la disponibilité d'un heap ESP32**.

## 2. Structures réelles et modèles mémoire

| Type | Rôle | Mesure |
|---|---|---|
| `BasicProgram` | Pointeur de stockage, capacité et longueur effective | `sizeof`, align |
| `BasicExecutor` | Programme emprunté, curseur et magasin emprunté | `sizeof`, align |
| `BasicSessionRuntime` | Pointeurs, **BasicExecutor intégré**, état | `sizeof`, align |
| `BasicVariableStore` | Pointeur de tableau + capacité + compteur | `sizeof`, align |
| `BasicVariableEntry` | Clé typée complète + valeur ; coût par case réservée | `sizeof`, align |
| `BasicVariableKey` | Type, longueur, 40 octets de nom | `sizeof`, align |
| `BasicVariableValue` | Type + union INTEGER16 / REAL5 / descripteur de chaîne | `sizeof`, align |
| `BasicProgramLine` | Métadonnées de parcours, **temporaires** | `sizeof`, align |
| `BasicVariableRef`, `BasicVariableName` | Décodeur / canonicalisation, temporaires | `sizeof`, align |
| `BasicStringValue` | Deux `uint32_t` réservés ; **aucune arène chaîne implémentée** | `sizeof`, align |
| `BSResult`, `BSRResult` | Résultats transportés par valeur | `sizeof`, align |
| `BasicVariableTypes` | 26 entrées A–Z (option future) | `sizeof`, align |

**Distinctions cruciales :**

- Coût fixe des descripteurs persistants = `sizeof(BasicProgram) + sizeof(BasicSessionRuntime) + sizeof(BasicVariableStore) + sizeof(BasicVariableTypes)`. **Ne pas additionner une seconde fois BasicExecutor**, déjà membre de BasicSessionRuntime. Une instance autonome d'exécuteur hors runtime serait un coût distinct.
- Programme réservé = `program.capacity` octets ; programme effectivement rempli = `program.size` (inclut deux octets de sentinelle). Les bytes non utilisés restent réservés par l'appelant.
- Magasin réservé = `variable.capacity * sizeof(BasicVariableEntry)`; `variable.count` cases sont occupées. Pour l'instant chaque entrée porte **une clé de 40 octets**, même si son nom est court. Les octets des futures chaînes ne sont **pas** comptés : non pris en charge.
- Source de ligne, buffer de tokenisation et buffer de sortie sont trois régions distinctes appartenant à l'appelant, **pas des champs du runtime**. Le buffer LIST est également celui de sortie de session, non un second buffer persistant.
- Les temporaires automatiques (`BEAssignment` dans `be_step`, `BasicProgramLine`, buffers `digits[]`, `encoded[43]`, tableaux d'aliasage) appartiennent à la **pile**, non à ces réservations.
- La table `BasicVariableTypes` est actuellement une structure indépendante, **pas une allocation automatique cachée** du runtime.

**Valeurs réellement mesurées sur GitHub Actions Linux x86-64**, ABI pointeur/size_t 8/8 octets, GCC 13.3.0, CMake 3.31.6, GNU Binutils 2.42. Les alignements proviennent de `offsetof` sur les vrais types du dépôt.

## 3. Scénarios de capacités

L'outil affiche pour chaque ligne : `fixed`, `program`, `entries`, `input`, `temp`, `output`, `reserved` (somme en octets) et `occupied*` (jeu d'occupation **hypothétique**, pas un relevé d'exécution).

| Scénario | Programme réservé / occupé hypoth. | Variables capacité / utilisées hypoth. | Entrée source / temp. / sortie réservées |
|---|---:|---:|---:|
| Petit | 1 024 / 320 o | 16 / 8 | 256 / 512 / 2 048 o |
| Moyen | 8 192 / 6 144 o | 64 / 48 | 512 / 2 048 / 4 096 o |
| Grand | 16 384 / 12 288 o | 128 / 96 | 512 / 2 048 / 8 192 o |
| Stress | 32 768 / 30 720 o | 256 / 240 | 1 024 / 2 048 / 16 384 o |

**Résultats chiffrés Linux (GCC 13.3, 64-bit) :**

| Scénario | Fixe | Programme réservé | Entrées réservées | Entrée + temporaire + sortie | Total réservé | Occupation hypothétique |
|---|---:|---:|---:|---:|---:|---:|
| Petit / 16 | 122 | 1 024 | 896 | 2 816 | **4 858 o** | 1 402 o |
| 8 Kio / 64 | 122 | 8 192 | 3 584 | 6 656 | **18 554 o** | 10 746 o |
| 16 Kio / 128 | 122 | 16 384 | 7 168 | 10 752 | **34 426 o** | 20 602 o |
| Stress / 256 | 122 | 32 768 | 14 336 | 19 456 | **66 682 o** | 54 010 o |

Les totaux ci-dessus sont ceux du programme de mesure exécuté par la CI, et non une simple extrapolation manuelle. `fixed` inclut le `BasicExecutor` intégré à `BasicSessionRuntime` ; aucune double comptabilisation.

Calcul exact du total réservé pour une ABI donnée :

```text
fixed = sizeof(BasicProgram) + sizeof(BasicSessionRuntime)
      + sizeof(BasicVariableStore) + sizeof(BasicVariableTypes)
entries = variable_capacity * sizeof(BasicVariableEntry)
reserved = fixed + program_capacity + entries
         + input_capacity + temporary_capacity + output_capacity
occupied_hyp = fixed + program_used_hyp + variable_count_hyp * sizeof(entry)
             + input_used_hyp + temp_used_hyp + output_used_hyp
```

**Attention :** `occupied_hyp` n'est pas le heap restant et n'a pas vocation à s'ajouter à `reserved`. Les coûts de l'allocateur, l'alignement des allocations, les stacks et les drivers ne sont pas inclus. Des capacités ne constituent pas une garantie de fonctionnement des instructions actuelles (grammaire encore partielle).

### Contraintes révélées par l'adaptateur hôte

La CLI de `host/loco_basic_cli.c` déclare `Cli cli;` **en variable automatique dans `main`**, avec ses tableaux intégrés : programme 32 768, magasin 64 entrées, entrée 512, temporaire 2 048, **sortie 131 072 octets**, plus descripteurs. Cette grosse allocation sur la pile principale Linux ne doit **pas** être copiée dans une tâche FreeRTOS ESP32. Une sortie de 4 Kio ou 8 Kio est un **choix de capacité**, pas la preuve que LIST d'un programme plein fonctionnera.

Le contrat actuel de `bl_list_program` est **atomique** : rendu validé puis vérification de la place avant émission. En particulier, pour un programme de 8/16 Kio, la taille LIST décodée peut dépasser un petit buffer de sortie. Il faudra soit réserver la capacité complète réellement nécessaire, soit (dans un **jalon ultérieur**) définir une interface LIST paginée/streamée qui préserve les invariants. **Aucun changement d'API effectué ici.**

## 4. Pile : examen et méthode

Points à surveiller en priorité :

| Chaîne de fonctions typique | Temporaires notables |
|---|---|
| `bsr_submit → bs_process_line → bt_tokenize → one_pass → explicit_variable` | `encoded[3 + 40]`, encodeur et métadonnées de passes |
| `bsr_submit → bs_process_line → bl_list_program → render → decode` | `BasicProgramLine`, `BLEmitter`, `digits[5]` ; deux passes successives |
| `bsr_step → be_step → execute_line → evaluate_integer_addition → bvb_read_explicit` | Deux `BEAssignment` dans `be_step`, une clé et une valeur locales en évaluation |
| `bsr_submit → submit_overlap` | tableaux `parts[9]` et `lengths[9]` : 9 pointeurs + 9 `size_t` |

**Frames GCC observées lors du build CI Linux Debug (octets par fonction, sans addition implicite) :**

| Fonction | Linux normal | ASan/UBSan |
|---|---:|---:|
| `bsr_submit` | 160 | 336 |
| `bs_process_line` | 160 | 288 |
| `bt_tokenize` | 128 | 256 |
| `one_pass` | 112 | 336 |
| `explicit_variable` | 176 | 352 |
| `bl_list_program` | 112 | 240 |
| `render` | 128 | 384 |
| `bsr_step` | 112 | 256 |
| `be_step` | 336 | 656 |
| `execute_line` | 304 | 736 |
| `evaluate_integer_addition` | 192 | 400 |
| `bvb_read_explicit` | 208 | 368 |

**Somme partielle, non-borne de pic :** la chaîne `bsr_step → be_step → execute_line → evaluate_integer_addition → bvb_read_explicit` totalise 1 152 o (Linux normal), ou 2 416 o sous ASan/UBSan, **avant** ses propres sous-appels, l'instrumentation réelle, l'ABI Xtensa et la pile appelante. Les frames marquées `dynamic,bounded` par GCC doivent être interprétées avec précaution.

Les frames GCC `.su` avec `-fstack-usage` sont des **estimations par fonction dans une configuration de compilation**, pas un maximum de pile de la chaîne. Les frames de fonctions sur le même chemin s'additionnent ; les passes validation/émission **séquentielles** ne doublent pas la pile à elles seules. Optimisation, inlining, instrumentation ASan et ABI peuvent changer ces chiffres. Une preuve finale impose l'examen des appels et un **high-water mark** de tâche sur ESP32 (`uxTaskGetStackHighWaterMark`) en charge représentative.

La recherche statique dans les dix fichiers `core/*.c` du dépôt courant n'a révélé **aucun appel explicite** à `malloc`, `calloc`, `realloc`, `free` ou `alloca`. Il s'agit d'un audit statique, non d'une démonstration instrumentée des dépendances libc. Les appels I/O de la CLI sont **hors cœur**. Prévoir plus tard un test d'interposition `malloc` ou une mesure de heap avant/après, en préservant le contrat caller-owned.

## 5. Flash : hôte et cible non interchangeables

**Mesures `size -A` du binaire `loco_basic_cli` sous Linux Debug** (octets, CI GCC 13.3) :

| Section | Sans sanitizers | ASan/UBSan |
|---|---:|---:|
| `.text` | 42 719 | 146 569 |
| `.rodata` | 2 180 | 31 888 |
| `.data` | 16 | 162 752 |
| `.bss` | 48 | 48 |

Le total `size -A` pour **toutes** les sections du fichier est respectivement de 111 218 o et 560 407 o : il ne correspond ni à la somme des seules quatre sections ci-dessus, ni à la taille d'une image ESP32. Le compteur `.bss` ne contient **pas** `Cli cli` puisqu'il est automatique sur la pile.

`size -A build/loco_basic_cli` liste les sections ELF hôte `.text`, `.rodata`, `.data`, `.bss` (ainsi que les autres sections). Ce binaire **inclut la CLI Linux et son environnement d'édition de liens** ; il ne constitue pas un firmware CYD. Des objets `core/*.o` et archives `libbasic_*.a` peuvent isoler le coût compilé brut, mais les sommes des sections objets ne sont pas l'image Flash finale et ignorent les effets de l'éditeur de liens. Sous ASan/UBSan, le binaire est également instrumenté et **ne convient pas** comme estimation de firmware.

Quand ESP-IDF sera disponible, bâtir un composant C99 minimal contenant les sources de `core/`, indépendant du HAL graphique, et un `app_main` qui ne fait qu'initialiser/tester le cœur. Séparer ce prototype du CMake Linux. Procédure cible **prévue, non exécutée** après installation/configuration d'une version ESP-IDF compatible ESP32 :

```sh
idf.py set-target esp32
idf.py build
idf.py size
idf.py size-components
idf.py size-files
```

Relever la configuration `sdkconfig`, version du compilateur Xtensa, table des partitions (4 Mo Flash), tailles DRAM/IRAM, Flash text/rodata et les blocs heap. Sans ce build, **aucune empreinte Flash ou SRAM ESP32 chiffrée n'est démontrée**.

## 6. Budget écran et système CYD (prévisionnel)

D'après la documentation Espressif, l'ESP32 classique comporte 520 Kio de SRAM interne au total, répartis en **320 Kio DRAM + 200 Kio IRAM** ; la DRAM libre, son plafond statique et sa disponibilité après système/pilotes ne valent pas 520 Kio. Voir :
- [Espressif — ESP32 memory types](https://docs.espressif.com/projects/esp-idf/en/v5.2.6/esp32/api-guides/memory-types.html).
- [Espressif — ESP32 datasheet](https://documentation.espressif.com/esp32_datasheet_en.html).

| Approche envisagée | Buffer minimal (calcul géométrique) | Lecture de risque |
|---|---:|---|
| Framebuffer TFT complet 320 × 240 RGB565 | **153 600 o (150 KiB)** | **Élevé / déconseillé** sans PSRAM ; pas de marge garantie pour heap, piles, pilotes |
| Framebuffer 320 × 200 RGB565 | 128 000 o (125 KiB) | Élevé ; le TFT entier doit encore être piloté |
| Buffer logique MODE 1 320 × 200, 2 bpp | **16 000 o** | **Plausible**, 4 indices couleur ; conversion en RGB565 pour émission |
| Buffer logique plein 320 × 240, 2 bpp | 19 200 o | Plausible mais pas un écran CPC MODE 1 historique |
| Une ligne TFT RGB565 | 640 o | Faible, dépend du protocole d'actualisation |
| 8 lignes TFT RGB565 | 5 120 o | Modéré, potentiellement compatible DMA sous réserve de capacité adaptée |
| Tuile 16 × 16 RGB565 | 512 o | Faible, gestion des pixels persistants à préciser |
| Texte seul 40 × 25 (codes de caractère uniquement) | 1 000 o | Insuffisant seul pour attributs, fenêtres, pixels modifiés et état graphique |

Les buffers de lignes/tuiles n'impliquent **pas** la gratuité du stockage de l'état graphique : `PLOT`, `DRAW`, le texte et les recolorations exigent une stratégie de cohérence (RAM logique 2 bpp, ou reconstitution, etc.). L'écran ILI9341 320 × 240 sera distinct du domaine logique CPC 320 × 200. Un buffer logique 2 bpp de 16 000 o plus un tampon de 8 lignes RGB565 de 5 120 o implique **21 120 o** de réserve graphique hors pilotes ; c'est un exemple, **pas un moteur livré**. Sous l'ABI Linux mesurée, cette stratégie ajoutée au scénario 8 Kio / 64 porte les seules réservations applicatives représentées à **39 674 octets** ; au scénario 16 Kio / 128, à **55 546 octets**. À l'opposé, stress 32 Kio / 256 + framebuffer complet RGB565 atteint déjà **220 282 octets** de buffers/descripteurs **avant** le système, les piles et le heap, illustrant le risque majeur sur CYD sans PSRAM.

**Marge système :** aucun chiffre de heap libre disponible n'est affirmé. Proposition de règle d'admission future : relever, **après initialisation** des tâches et pilotes SPI/ILI9341/XPT2046/SD, `heap_caps_get_free_size(MALLOC_CAP_8BIT)`, `heap_caps_get_largest_free_block(MALLOC_CAP_8BIT)`, `heap_caps_get_minimum_free_size(MALLOC_CAP_8BIT)` et la marge de pile de chaque tâche. Garder **au minimum 64 KiB de heap 8-bit libre** comme **objectif d'ingénierie à valider**, en plus de l'ensemble des buffers et des réserves système ; si ce seuil n'est pas atteignable, reconsidérer les capacités et les périphériques. Le plus gros bloc doit suffire à chaque allocation contiguë requise ; la somme libre ne suffit pas à prouver cela. Le coût du Wi-Fi/Bluetooth éventuel n'est pas budgété : fonctionnalités ultérieures désactivées durant la preuve initiale.

## 7. Décisions de capacité provisoires

**Cible conservatrice proposée avant mesure matérielle :** programme **8 Kio**, **64 entrées scalaires** (REAL5/STRING non pleinement exécutables), source 512 o, temporaire 2 Kio, et **4–8 Kio de sortie** selon LIST attendu ; plus une surface logique MODE 1 de 16 000 o et **jusqu'à 5 120 o de lignes RGB565** lorsque l'affichage sera intégré. Les plafonds ne sont pas des limites CPC et ne doivent pas être figés dans les interfaces publiques.

**16 Kio / 128 entrées** = objectif secondaire conditionné à la mesure du heap et de LIST. **32 Kio / 256 entrées + framebuffer RGB565** = scénario stress à **risque élevé**, sans garantie de faisabilité.

## 9. Verdict

**Plausible mais non démontrée sur ESP32 CYD.** La conception caller-owned donne un contrôle explicite des buffers et des tableaux, et les stratégies d'affichage compact ont des coûts géométriquement compatibles avec un budget modeste. En revanche, **ni les 520 Kio bruts ni les mesures Linux ne prouvent la quantité allouable sur une carte CYD**, surtout sans PSRAM. La preuve de faisabilité matérielle demeure **non vérifiée** tant que l'intégration C99 minimale, le linker ESP-IDF et les métriques heap/stack réelles ne sont pas collectés.

**J0.24 non engagé.** La prochaine priorité pressentie après revue Pilotage est un premier banc différentiel indépendant face à un véritable Locomotive BASIC 1.1 de CPC 6128.
