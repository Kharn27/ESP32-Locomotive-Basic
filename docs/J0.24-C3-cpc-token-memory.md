# J0.24-C3 — Extraction indépendante des programmes BASIC tokenisés en RAM

**Acquisition et comparaison historiques réussies le 25 octobre 2026.** Deux véritables images RAM de Locomotive BASIC 1.1, prélevées sous CPC 6128 / Caprice32 4.6.0 et conservées octet pour octet dans `tests/fixtures/cpc6128/token_ram/`, sont identiques à l'export C99 pour les deux sources concernées. **J0.24 demeure ouvert** : seulement deux cas indépendants vérifiés sur au moins huit requis. PR #36 soumise à Pilotage sans fusion ni lancement de J0.25.

## Indépendance de la localisation et mapping RAM/SNA

L'identification de la mémoire repose sur le désassemblage ROM BASIC 1.1 `basic.asm`, notamment les chemins de création, stockage et parcours du programme (début de zone et recherche de fin). L'analyse n'utilise **jamais les tokens C99 pour rechercher la zone mémoire CPC**.

- Pointeur historique de base du programme : `(&AE64)`, mesuré `&016F` sur les deux acquisitions.
- Le premier mot de longueur est à `P+1 = &0170` ; `[P]` vaut `00` et reste hors de l'image brute exportée.
- Pointeur historique de premier octet libre : `(&AE66)`, mesuré `&018E` et `&019E`. La vérification suit tous les enregistrements depuis `P+1` jusqu'à `E`, inclusivement pour la sentinelle au sein de `[P+1,E)`. La frontière est donc dérivée de la ROM, non de notre tokenizer.
- `src/slotshandler.cpp` du Caprice32 épinglé, dans `snapshot_save()`, écrit `sizeof(t_SNA_header)` puis `pbRAM` sur `CPC.ram_size * 1024` octets. Selon `src/cap32.h`, l'en-tête SNA v3 est de 256 octets. Snapshot transitoire attendu : 256 + 131072 octets ; signature `MV - SNA`, version 3, modèle CPC6128, 128 Ko, banque RAM configuration zéro.
- Le programme est dans la RAM physique banque 0 : offset dans le fichier snapshot temporaire **`0x100 + 0x170 = 0x270`**, soit 624 décimal. Les pointeurs `&AE64`/`&AE66` sont des adresses RAM vues par la ROM et consultées dans cette même image physique, pas des données ROM redistribuées.

Les octets sources ASCII originaux `tests/fixtures/cpc6128/sources/b_integer_scalar.bas` et `c_integer_add.bas` restent non modifiés. Vérification systématique des longueurs, numéros strictement croissants, terminateurs, sentinelle, adresses, offsets et SHA-256. Le composant RAM et le C99 n'ont subi aucune adaptation pour « fabriquer » une correspondance.

## Méthode de capture avant RUN et piège Caprice32

Automatisation `--autocmd` : saisie des lignes numérotées, commande `LIST`, deux délais, `CAP32_SCRNSHOT`, capture `CAP32_SNAPSHOT` puis `CAP32_EXIT`. **Aucune commande RUN n'est émise** avant le prélèvement RAM. Les PNG de `LIST` dans l'artefact montrent réellement le bandeau `BASIC 1.1`, les sources et leur réaffichage. Les PNG sont des témoins visuels, pas des images mémoire ni des flux `PRINT`.

**Limitation expérimentale du Caprice32 figé :** `src/argparse.cpp` omet `CAP32_SNAPSHOT` dans `replaceCap32Keys()`, bien que `src/keyboard.h`, `src/keyboard.cpp` et `src/cap32.cpp` le prennent en charge. L'envoi littéral du nom échouait : snapshot absent. Notre pilote encode l'événement reconnu par Caprice32 (préfixe form-feed `0C`, puis `0D`, code `MOD_EMU_KEY+13`), en conservant la commande symbolique d'intention dans `autocmd.json`. L'émulateur et son SHA restent **inchangés**. Le test suivant a relevé la base réelle `&016F` et permis de corriger une borne minimale trop restrictive dans l'extracteur ; aucune correction sur les données extraites.

L'intégralité du SNA n'est **jamais archivée** : elle existe seulement dans un `TemporaryDirectory` du runner CI, détruit même en erreur. Seules les deux images `program.bin` brutes, les deux images C99 indépendantes, les métadonnées et les témoins autorisés sont exportés. Aucune ROM, image de RAM complète ou fichier `.sna` n'est committé ou publié. Aucun contenu issu du dépôt de ROM propriétaire n'est distribué hors des *brefs extraits tokenisés générés par l'interpréteur* ; les droits sur les logiciels d'origine restent à respecter.
