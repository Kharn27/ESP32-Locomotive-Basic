# J0.24-C6 — Première mesure comportementale indépendante de RUN

**Acquisition réalisée le 25 octobre 2026.** Deux programmes, deux nouvelles
sessions Caprice32, un CPC 6128 (128 Kio) et sa ROM Locomotive BASIC 1.1
authentifiée. **Résultat : deux MATCH_SEMANTIC sur une valeur INTEGER après
RUN.** Cela ne vaut ni conformité exacte de la sortie écran, ni homologation
générale de RUN, ni validation ESP32.

## 3. Protocole et mesures

Pour **chaque programme**, `run_behavior_oracle.py` lance un **nouveau
processus Caprice32**, injecte les quatre lignes BASIC inchangées, puis
`RUN` et, après RUN dans la même session, la commande directe
`PRINT #8,B%`. La sonde n'est pas stockée dans le programme original.
Une capture PNG est prise après le déroulement. Le CLI C99 est exécuté
séparément avec l'entrée brute contenant `RUN`, `:step 100` et `:quit`.

| Cas | CPC par sonde imprimante | C99 stdout après RUN | Statut |
| --- | ---: | ---: | --- |
| C — addition INTEGER | 5 | 5 | `MATCH_SEMANTIC` |
| D — auto-référence INTEGER | 2 | 2 | `MATCH_SEMANTIC` |

Les valeurs 5 et 2 étaient des **hypothèses avant acquisition** ; elles sont
devenues des observations vérifiées seulement après lecture et contrôle
des octets CPC et C99 archivés. Le comparateur lit un **unique entier signé
16 bits**, sur une ligne terminée par CR, LF ou CRLF et n'effectue aucune
normalisation générale. Les octets imprimante et stdout **diffèrent**.

| Fichier / SHA-256 | Programme C | Programme D |
| --- | --- | --- |
| PNG écran | `d0d15378eee3eb763390c1e0e592730e9260c0dcc6d7c832bcc7212d50e625b1` | `3a16418c12d0aaf18e12d1525989a4d75dc86337073c34351259960e49854afa` |
| `printer.dat` | `427c73eb948406e2dee128c2e23ee2dfc00e26e35f6b776a7d7112a1e9996246` | `a6b9d0e774e8414383a7154ccc19fb4da0057614ddd554ad96789ac8d5ede99e` |
| `native.stdout.bin` | `f0b5c2c2211c8d67ed15e75e656c7862d086e9245420892a7de62cd9ec582a06` | `53c234e5e8472b6ac51c1ae1cab3fe06fad053beb8ebfd8977b010655bfdd3c3` |

Les fichiers `source.bas`, `autocmd.json`, `cap32.cfg`,
`caprice.log`, `native.stdin.bin` et `native.stderr.bin` sont eux
aussi archivés **bruts** avec tailles et SHA-256.

## 4. Trois niveaux qui restent distincts

1. **TOKENS :** huit images RAM authentiques C3/C4/C5, toujours
   `MATCH_EXACT` octet par octet. Leur comparaison est indépendante
   des présentes sondes.
2. **RUN_NUMERIC_PROBE :** C et D sont `MATCH_SEMANTIC` pour **B% après RUN**
   sur la seule base de la lecture imprimante et de stdout C99.
   Des valeurs différentes produiraient `DIFF`.
3. **RUN :** le formatage exact des caractères **écran CPC** demeure
   `UNVERIFIED`. Le PNG est une preuve visuelle, pas un flux de texte
   permettant une comparaison byte-à-byte. Aucune classification
   `MATCH_EXACT` de RUN ne découle de la sonde.

L'opération `RUN_NUMERIC_PROBE` est ajoutée uniquement pour les cas C et D
au manifeste différentiel. Les observations `RUN` et `LIST` historiques
ne sont pas détournées.

## 5. Vérifications et sécurité des archives

`tests/oracles/cpc_run_evidence.py` valide les hashes de tous les fichiers,
la provenance du run et de l'artefact, le lien immuable vers le manifeste
d'acquisition, les sources historiques, la configuration CPC, la chronologie
`RUN` puis sonde directe, la présence du screenshot et de la sortie
imprimante, les canaux C99 séparés et la classification recalculée.

Les tests négatifs refusent entre autres les modifications des octets CPC
ou C99, sources historiques, PNG manquants, preuves imprimante absentes,
ordre sonde/RUN inversé, falsifications des valeurs, classifications
`MATCH_EXACT` et confusions entre écran, imprimante et stdout.
La nouvelle suite CTest permanente est la **24e** et conserve les 23 suites
précédentes. Le workflow Caprice32 regénère en outre les deux programmes C/D
sur un nouveau run et revérifie les huit fixtures tokenisées C3/C4/C5.

### Reproduction

```sh
python3 tests/oracles/run_behavior_oracle.py \
  --caprice tests/oracles/caprice32 \
  --native-cli build/loco_basic_cli \
  --output /tmp/cpc-run-behavior

python3 tests/oracles/cpc_run_evidence.py \
  --evidence /tmp/cpc-run-behavior --self-test

python3 tests/oracles/cpc_run_evidence.py \
  --evidence tests/fixtures/cpc6128/run_behavior \
  --permanent --self-test
```

La reproduction exige le Caprice32 épinglé compilé et une ROM autorisée ;
la vérification des **preuves déjà archivées** n'en dépend pas.

## 6. Limites et décision réservée à Pilotage

Cette première mesure couvre **deux cas simples**, non les erreurs
historiques, la totalité des variables et expressions, le format écran
CPC, ni les contraintes réelles de Flash/RAM/pile sur Xtensa. Le cœur C99
et ses opérations arithmétiques n'ont pas été modifiés pour obtenir une
concordance.

J0.24 et J0 **restent ouverts**. La PR C6 n'est **pas auto-fusionnée** :
Pilotage doit examiner les données archivées, le dernier HEAD et les
résultats CI avant toute décision d'acceptation.

## 8. C6-C1 — Renforcement après revue Pilotage

**Correction sur la PR #42 existante ; aucune extension fonctionnelle du langage.**
Les observations originales de l'acquisition #40241824206 et leurs octets
restent inchangés ; les tests sont exécutés sur des **copies temporaires**.

### Ancrage historique hors des manifestes

Le vérificateur `tests/oracles/cpc_run_evidence.py` contient les constantes
d'approbation Pilotage suivantes, indépendantes des fichiers contrôlés :

- `APPROVED_ACQUISITION_SHA256 = 2e39584df89089120f422a0c7cd3541ac5e0b9a4f24788007b31c9d3cc34b895`
- `APPROVED_GITHUB_RUN_ID = 40241824206`
- `APPROVED_ARTIFACT_ID = 12615969513`

En mode `--permanent`, le digest des **octets** de `acquisition.json`,
celui enregistré dans `manifest.json`, le run et l'artefact doivent tous
correspondre à ces constantes. Les autres contrôles SHA, fichiers, provenance
et classifications sont conservés. Un test négatif remplace les octets
`printer.dat` par une valeur numérique équivalente, recalcule les
descripteurs et **les deux manifestes**, y compris le nouveau digest
d'acquisition, puis vérifie que le refus est explicitement dû à l'**ancrage
immuable**. Les constantes ne sont jamais produites à partir du contenu
à valider. Comme tout contrôle versionné dans le dépôt, cet ancrage suppose
que les modifications du code du vérificateur font l'objet d'une revue.

### Deux modes de provenance

- **Temporaire / local** : `GITHUB_RUN_ID` et `GITHUB_SHA` peuvent tous
  deux être absents ; une paire partielle ou mal formée reste rejetée.
  Les checksums, sources, commandes, canaux et classification restent
  strictement vérifiés. L'acquisition produite par le script ne revendique
  alors aucun run ou artefact GitHub.
- **Permanent** : les deux champs GitHub valides sont obligatoires ;
  le run ID doit être celui approuvé, et l'ensemble
  run/artefact/digest originaux est strictement épinglé.

La reproduction locale du §5 fonctionne sans variables GitHub Actions.
Le workflow rejoue en outre une acquisition CPC complète en retirant
explicitement ces variables (`env -u GITHUB_RUN_ID -u GITHUB_SHA`), puis
valide les preuves obtenues.

### Barrière comportementale CI, distincte de la validation structurelle

```sh
python3 tests/oracles/cpc_run_evidence.py \
  --evidence /tmp/cpc-run-behavior --self-test

python3 tests/oracles/cpc_run_evidence.py \
  --evidence /tmp/cpc-run-behavior --require-accepted-behavior
```

Le premier appel **archive et valide** honnêtement les mesures
`MATCH_SEMANTIC`, `DIFF`, `UNVERIFIED` ou `UNSUPPORTED`, sans transformer
ces dernières en concordances. Le second représente la **barrière
d'acceptation CI** : il exige exactement les deux programmes C/D,
`CPC=5, C99=5, MATCH_SEMANTIC` et
`CPC=2, C99=2, MATCH_SEMANTIC`. Toute anomalie retourne un **code non nul**.
La CI utilise un step dédié et conserve `if: always()` pour téléverser
les données diagnostiques C6 même en cas d'échec du gate.

Les tests négatifs du vérificateur prouvent la sortie non nulle du vrai
programme CLI pour : `DIFF`, `UNVERIFIED`, `UNSUPPORTED`, une
fausse concordance numérique (par exemple 6/6 au lieu de 5/5), et
l'absence d'un des deux cas. Les données invalides ne sont jamais
promues dans le corpus historique.

**Limites inchangées :** `RUN_NUMERIC_PROBE` compare une valeur entière
après `RUN` ; la sortie CPC *écran* reste `UNVERIFIED` au niveau
octet par octet. J0.24 et J0 restent ouverts, décision finale Pilotage.
