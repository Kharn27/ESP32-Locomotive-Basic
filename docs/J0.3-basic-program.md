# J0.3 — Module C99 basic_program (en revue)

**Périmètre :** stockage, parcours, validation, import/export et mutations d'une
image tokenisée déjà produite. Aucune analyse de texte, exécution ou détokénisation.

**Références :** [J0.1](J0.1-architecture-locomotive-basic-1.1.md),
[J0.2](J0.2-format-binaire-tokens.md), désassemblage basic.asm :
E761/E864 (structure et sentinelle), E7A5–E7DE (mutations), ED19–ED24
(export sans garde). Les vecteurs J0.2 sont des déductions statiques, et non
des captures CPC indépendamment validées.

## Format retenu

- Longueur d'enregistrement u16 little-endian (5 à 65535 octets),
  suivie du numéro u16 little-endian (1 à 65535), du corps opaque,
  puis d'un terminateur 00 inclus dans la longueur.
- Lignes strictement croissantes, puis sentinelle 00 00. Le programme
  vide occupe deux octets, sans octet de garde RAM historique.
- Le 00 dans les tokens est une donnée ordinaire; seul l'octet placé à
  offset + longueur - 1 est l'indicateur de fin d'enregistrement.
- Import/export conservent tous les octets d'une image structurellement
  valide. Aucune conversion de référence 1D/1E ni interprétation de tokens.

## API publique (core/basic_program.h)

| Fonction | Comportement |
|---|---|
| bp_init(p, storage, capacity) | Initialise à deux zéros, size=2; capacité minimale 2 |
| bp_validate_image(image, length) | Valide exactement une image binaire externe |
| bp_validate(p) | Vérifie size <= capacity et la structure |
| bp_import(p, image, length) | Valide avant copie, puis remplace le programme |
| bp_export(p, dest, capacity, written) | Exporte la copie exacte des size octets |
| bp_put(p, number, body, length) | Insère ou remplace, ajoute le 00 final |
| bp_delete(p, number) | Supprime une ligne ou renvoie BP_NOT_FOUND |
| bp_find(p, number, line) | Recherche numéro, offsets, longueur du corps |
| bp_next(p, cursor, line) | Parcourt les enregistrements, BP_END à la sentinelle |

Le paramètre body_length exclut **toujours** le terminateur 00, que le
module ajoute automatiquement. Un corps vide est structurellement autorisé
(enregistrement de longueur 5). La sémantique CPC de saisie d'un numéro seul
(suppression de ligne) appartiendra au futur éditeur, non à ce module.

BasicProgramLine fournit offset (début enregistrement), next_offset,
body_offset, body_length (sans terminateur), number. Le corps est accessible
par p->data + body_offset, pour body_length octets seulement.

Pour parcourir, initialiser un curseur size_t à 0 et appeler bp_next tant
que BP_OK. BP_END signale la sentinelle, et laisse le curseur inchangé.
Ne pas fournir de curseur arbitraire : utiliser les offsets provenant de
l'API. **Chaque mutation réussie invalide tous les offsets, curseurs et
pointeurs calculés à partir du programme**, même un remplacement. Rechercher
à nouveau après mutation.

## Contrat de propriété, erreurs et atomicité

Le buffer est fourni, possédé et maintenu vivant par **l'appelant**.
La structure BasicProgram emprunte ce buffer, sans malloc, mémoire globale,
allocation de chaîne ou index caché. Toute modification externe de la
mémoire doit être suivie d'un appel à bp_validate avant de l'exploiter.

bp_import, bp_export et bp_put interdisent tout **chevauchement** entre
source/destination et la **capacité entière** du stockage du programme.
BP_OVERLAP est renvoyé sur Linux/ESP32 (uintptr_t disponible).
Sur les cibles ISO C99 sans uintptr_t, l'absence de chevauchement constitue
une précondition non détectable. Les arguments de type pointeur doivent
correspondre à une zone accessible d'au moins la taille annoncée : une
fonction C ne peut pas vérifier la réalité de cette allocation. Le paramètre
written d'export doit être un pointeur distinct du stockage. En cas de
multitâche, la synchronisation relève de l'appelant.

Codes de retour : BP_OK, BP_END (fin normale du parcours),
BP_NOT_FOUND (numéro absent), BP_INVALID_ARGUMENT (pointeur ou paramètre
manquant), BP_INVALID_LINE_NUMBER (zéro), BP_BAD_FORMAT (longueur trop courte,
numéro nul, ordre/doublon, mauvais terminateur, données après la sentinelle),
BP_TRUNCATED (champ ou sentinelle manquante, longueur au-delà de l'image),
BP_NO_SPACE (capacité insuffisante), BP_OVERFLOW (ligne dépassant u16),
BP_OVERLAP (alias interdit). Ce sont des erreurs **internes** et non une
conversion prétendue vers les messages historiques CPC.

La validation et les contrôles de longueur/capacité précèdent les écritures
et tous les appels memmove/memcpy. Un échec de bp_put, bp_delete, bp_import
ou bp_export ne modifie pas les octets utiles ni la taille du programme.
Un export raté laisse written inchangé. Les octets de réserve après size
ne sont pas effacés.

## Coût mémoire et complexité

Le stockage est compact et continu, sans pointeur persistant ni index.
Chaque ligne coûte 5 octets d'encadrement, auxquels s'ajoutent les tokens.
La sentinelle de fin occupe 2 octets. La seule RAM permanente propre au
module est le descripteur (trois champs : pointeur, capacité, taille).
Pas de heap ni de tampon temporaire de la taille du programme.

Validation et recherche : O(nombre de lignes). Insertion, remplacement,
suppression : O(nombre de lignes + octets décalés), par memmove borné.
Parcours bp_next : O(1) par enregistrement pour un curseur valide.
Il n'y a aucune limite totale artificielle de 64 Ko : la longueur
**de chaque ligne** est codée en u16; le programme entier est limité
par la capacité allouée et size_t.

## Tests Linux et CI

Compilation C99 stricte, GCC/Clang :
- cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
- cmake --build build --parallel
- ctest --test-dir build --output-on-failure

Sanitizers :
- cmake -S . -B build-asan -DCMAKE_BUILD_TYPE=Debug -DBP_SANITIZERS=ON
- cmake --build build-asan --parallel
- ctest --test-dir build-asan --output-on-failure

Les avertissements -Wall -Wextra -Wpedantic -Wconversion sont traités
comme des erreurs. Les tests couvrent les 15 cas demandés, contrôle
d'invariants après mutations, échecs atomiques, corps binaires avec 00,
valeur 65535, chevauchements et 500 mutations pseudo-aléatoires
déterministes. Les vecteurs J0.2 F3, F4 et F1bis restent **déduits**,
non « golden CPC ». Le workflow GitHub Actions exécute deux variantes :
Linux ordinaire et Linux sous AddressSanitizer + UndefinedBehaviorSanitizer.

## Exclusions et limitations

Ce module ne tokenise pas, ne détokénise pas, n'exécute pas de BASIC,
n'implémente ni LIST/RUN/NEW, ni microSD/HAL/firmware/écran.
Il ne décide pas si les tokens sont sémantiquement corrects pour un CPC,
ne résout pas les pointeurs 1D et ne prétend pas valider la compatibilité
binaire sans capture CPC indépendante.
