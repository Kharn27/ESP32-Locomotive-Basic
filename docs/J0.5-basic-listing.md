## Objet et limites

Transformation pure de données, sans exécution BASIC, console, dépendance ESP32, allocations, état global mutable ni rendu CPC. `basic_listing` accepte strictement le sous-ensemble J0.4 : PRINT (BF), LIST (A7), RUN (CA), NEW (B1), GOTO (A0), séparateur (01), petits entiers (0E..17), entier 8 bits (19 xx, >= 10) et référence de ligne 1E lo hi non nulle dans un contexte GOTO. Une référence GOTO n'est jamais devinée hors contexte, et le 1D de références résolues n'est pas implémenté.

**Niveau de preuve** : les tokens sont spécifiés par J0.2 et utilisés par J0.4, eux-mêmes déduits de la lecture statique `basic.asm`. Les essais aller-retour vérifient la cohérence interne du projet, pas une capture CPC indépendante. Le listing natif CPC réel (espacements, contrôle écran, couleurs, lignes et entrées/sorties) reste à confronter à une référence. LF (0A) entre lignes est **uniquement** une convention du cœur portable. Les octets >=80 dans les guillemets sont recopiés inchangés, **sans UTF-8 implicite**.

## API

~~~c
BLStatus bl_detokenize(const uint8_t *body, size_t body_length,
                       uint8_t *destination, size_t destination_capacity,
                       size_t *written);
BLStatus bl_list_program(const BasicProgram *program,
                         uint8_t *destination, size_t destination_capacity,
                         size_t *written);
~~~

- `bl_detokenize` consomme un corps binaire **sans** le 00 final (comme produit par J0.4 et fourni par J0.3). Le texte retourné ne comprend ni préfixe de ligne ni terminateur NUL ; `*written` indique son nombre d'octets exact.
- `bl_list_program` valide la structure `BasicProgram` via J0.3, puis émet les lignes en ordre croissant : numéro ASCII + **un espace ajouté** + corps décodé + LF. Un corps vide produit donc un espace puis un LF après le numéro. Un programme vide retourne 0 octet.
- Les espaces préexistants du corps, y compris avant le premier mot-clé, avant/après deux-points ou à la fin, sont conservés. Une chaîne sans guillemet final demeure sans fermeture. Les octets entre guillemets ne sont pas interprétés comme des tokens.
- Les nombres sont écrits en décimal sans zéros de tête ; le raccourci `?` est restitué comme PRINT. Aucun traitement de la casse ne touche les chaînes.
- Les appels utilisent des longueurs `size_t` explicites : ni `strlen` sur flux binaire ni limite globale 64 Ko, hormis les limites u16 **par enregistrement** imposées par J0.3.

## Erreurs et atomicité

`BL_OK`, `BL_INVALID_ARGUMENT`, `BL_NO_SPACE`, `BL_OVERFLOW`, `BL_OVERLAP`, `BL_UNKNOWN_TOKEN`, `BL_TRUNCATED`, `BL_BAD_SEQUENCE` et `BL_BAD_PROGRAM` sont des diagnostics C internes, jamais des numéros d'erreur CPC.

La validation et le calcul de taille précèdent **toute écriture** ; une deuxième passe émet la sortie. Un buffer insuffisant, un token inconnu, une donnée tronquée, un flux invalide, un alias interdit ou une image de programme invalide laissent **l'intégralité de la destination et `*written` intacts**. Le programme et le corps doivent demeurer immuables pendant les deux passes.

- `BL_UNKNOWN_TOKEN` : token hors dictionnaire J0.4 en position interprétée (dont 18, 1D, FF).
- `BL_TRUNCATED` : octets manquants après 19 ou 1E.
- `BL_BAD_SEQUENCE` : suite impossible à re-tokeniser avec la grammaire J0.4 (GOTO sans ligne, référence 0000, deux-points initial/doublé/final, opérande sans séparation, données littérales illégales, NUL/CR/LF dans une chaîne). La syntaxe des variables, réels, REM/DATA n'est pas devinée.
- `BL_BAD_PROGRAM` : validation structurale J0.3 refusée.
- `BL_OVERLAP` : recouvrement source/destination/`written`, y compris la totalité de la capacité destination et le stockage réservé `BasicProgram`. Vérification via uintptr_t sur Linux/ESP32 ; précondition de non-chevauchement sur une plateforme C99 sans uintptr_t.

Le décodeur accepte une chaîne non fermée sans inventer de guillemet. Un deux-points entre guillemets n'est jamais séparateur. Les NUL/CR/LF sont refusés par J0.4 même en chaîne, et sont donc également rejetés ici ; les autres octets non ASCII sont conservés tels quels.

## Validation

CTest ajoute `basic_listing` aux tests existants `basic_program` et `basic_tokenizer`. Vecteurs unitaires pour tous les tokens, entiers, références, espaces, commandes multiples, chaînes littérales/non closes/8 bits, images invalides, capacité exacte, erreurs atomiques et alias ; essais aller-retour `bt_tokenize -> bl_detokenize -> bt_tokenize` comparés **octet pour octet**. Un test `bt_tokenize -> bp_put -> bl_list_program` vérifie numérotation, ordre et LF. Les vecteurs J0.2 ne constituent pas des captures CPC indépendantes.

~~~sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --parallel
ctest --test-dir build --output-on-failure

cmake -S . -B build-asan -DCMAKE_BUILD_TYPE=Debug -DBP_SANITIZERS=ON
cmake --build build-asan --parallel
ctest --test-dir build-asan --output-on-failure
~~~

Compilation du projet : C99 strict, -Wall -Wextra -Wpedantic -Wconversion -Werror. Vérifier les runs GitHub Actions de la PR pour les preuves effectives.

## Hors périmètre

Aucun parseur général, interpréteur, exécution de LIST/RUN/GOTO/PRINT/NEW, éditeur interactif, gestion de variables, ressources audio/vidéo, microSD ni firmware ESP32. Aucun changement d'API J0.3/J0.4.
