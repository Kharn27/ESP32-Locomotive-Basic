# J0.6 — Session de saisie BASIC (accepté et fusionné)

**Statut :** accepté par Pilotage le 23 octobre 2026, intégré à `main` via [PR #6](https://github.com/Kharn27/ESP32-Locomotive-Basic/pull/6) (squash `486db356117cb36a7533b7477e37f78fe2c34e6f`). CI Linux et ASan/UBSan : 4/4 tests chacune.

**Périmètre :** édition de lignes numérotées, LIST et NEW directs, sans exécution, REPL, UART ni dépendance matérielle. Il s'agit d'un **contrat d'interface hôte provisoire**, pas d'une reconstruction de l'éditeur historique CPC.

## API et séparation des modules

```c
BSResult bs_process_line(BasicProgram *program,
                         const uint8_t *source, size_t source_length,
                         uint8_t *temporary, size_t temporary_capacity,
                         uint8_t *output, size_t output_capacity,
                         size_t *written);
```

Le module réutilise `bt_tokenize` pour produire le corps tokenisé (sans 00 final), `bp_put` pour ajouter le marqueur de fin 00 et gérer l'insertion/remplacement trié, `bp_delete` pour la suppression, `bp_validate` pour l'intégrité, `bp_init` pour réinitialiser sans allocation et `bl_list_program` pour LIST. Aucun changement des API J0.3/J0.4/J0.5 ni du format persistant : longueur u16 LE, numéro u16 LE, corps, 00, sentinelle 00 00.

Tous les arguments pointeurs sont requis, y compris quand une longueur/capacité vaut 0. `source_length` est une longueur exacte : **ne pas inclure le NUL terminal** d'une chaîne C. Le buffer temporaire est prêté par l'appelant ; sa capacité doit accueillir le corps effectivement produit par `bt_tokenize` (sinon `BT_NO_SPACE`). La limite structurelle de `bp_put` est `UINT16_MAX - 5` octets de corps par ligne. L'absence d'allocateur impose au transport de dimensionner temporaire et sortie. `output` n'est utilisé que par LIST et aucun NUL supplémentaire n'est ajouté. En succès, `*written` est la taille du listing ou zéro pour toute opération sans sortie.

## Règles de saisie J0.6

- Premier caractère chiffre ASCII : ligne numérotée, 1 à 65535, sans blancs devant. Les zéros initiaux sont admis ; la conversion contrôle l'overflow *avant* la multiplication, y compris pour une suite de chiffres très longue.
- Après les chiffres, fin de ligne ou **un seul** espace ASCII séparateur. Les espaces supplémentaires sont conservés dans le corps. `10PRINT 1` ou `10:PRINT 1` est refusé, contrairement à `10 PRINT 1`.
- Un numéro seul, ou suivi uniquement d'espaces ASCII, supprime la ligne. Si elle est absente, `BS_NOT_FOUND` est renvoyé sans mutation. Les instructions numérotées passent par la seule grammaire J0.4 : PRINT, LIST, RUN, NEW, GOTO, formes et arguments limités décrits dans [J0.4](J0.4-basic-tokenizer.md). Leur stockage n'entraîne aucune exécution.
- Hors numéro initial, les commandes directes sont reconnues après retrait des espaces ASCII en tête et fin, sans distinction de casse. **Seules** LIST et NEW sans argument sont autorisées. RUN, PRINT et GOTO directs : `BS_UNSUPPORTED_DIRECT`. Deux commandes séparées par `:` hors chaîne : `BS_MULTIPLE_DIRECT`, avant tout effet.
- Une entrée vide ou exclusivement constituée d'espaces est `BS_OK`, sans effet, avec `*written=0`. Les NUL, CR et LF à l'intérieur de la longueur fournie sont `BS_MALFORMED_INPUT`; leur suppression éventuelle revient au futur transport. Les tabulations ne sont pas normalisées.

Cette convention ne garantit pas la fidélité aux règles de saisie CPC historiques. LIST reprend les conventions hôte J0.5 (nombre ASCII, espace ajouté, corps détokénisé, LF) et non celles de l'affichage firmware CPC. Les octets non ASCII entre guillemets restent bruts.

## Retour des erreurs

`BSResult.status` vaut `BS_OK`, `BS_NOT_FOUND`, `BS_INVALID_ARGUMENT`, `BS_OVERLAP`, `BS_INVALID_LINE_NUMBER`, `BS_MALFORMED_INPUT`, `BS_MULTIPLE_DIRECT`, `BS_UNSUPPORTED_DIRECT`, `BS_TOKENIZER_ERROR`, `BS_PROGRAM_ERROR` ou `BS_LISTING_ERROR`. Si une erreur provient d'un sous-module, le champ associé du résultat retourne **sans perte** son statut natif : `tokenizer_status` pour `BT_*`, `program_status` pour `BP_*`, `listing_status` pour `BL_*`. Les deux autres valent `BT_OK`, `BP_OK`, `BL_OK`. Cela permet de distinguer `BT_NO_SPACE` de `BP_NO_SPACE` et `BL_NO_SPACE`, ainsi que les images corrompues et tokens inconnus. Ce sont des diagnostics C, pas des codes d'erreurs ROM CPC.

**Atomicité :** pour tout résultat autre que `BS_OK`, le programme (taille et contenu), **tous** les octets du tampon de sortie, et `*written` sont inchangés. Le temporaire peut être altéré après une tokenisation réussie puis un `BP_NO_SPACE`. LIST s'appuie sur les deux passes validantes de J0.5. NEW est effectué avec `bp_init` après contrôle d'intégrité et réemploie le même stockage ; il ne cherche pas à réparer une image corrompue.

Les six zones (structure `BasicProgram`, capacité complète du stockage, longueur source, capacité temporaire, capacité de sortie, objet `*written`) sont **mutuellement disjointes**. Le chevauchement est détecté via `uintptr_t` sur Linux/ESP32, et constitue une précondition de l'appelant sur les plateformes C99 sans `uintptr_t`. Toute capacité déclarée doit correspondre à une zone mémoire réellement accessible, immuable durant la validation (hormis les mutations autorisées du programme).

## Budget mémoire

**Surcoût permanent : 0 octet.** Pas de stockage global mutable, allocation dynamique, VLA, cache ni copie intégrale du programme. La pile contient seulement des scalaires, statuts, deux tableaux fixes de six entrées (pointeurs et longueurs) pour la vérification d'alias, et le résultat. Le programme, la sortie et le temporaire sont des buffers distincts *déjà alloués par l'appelant*, dont la capacité reste réglable. Le listing peut dépasser la longueur tokenisée, aussi `output_capacity` est indépendant de `temporary_capacity`. Aucune PSRAM requise.

## Validation

`tests/test_basic_session.c` couvre ordre, remplacement, suppression présente/absente, bornes 1/10/65535, zéros initiaux, chiffres excessifs, espaces, refus d'entrées erronées/non supportées, capacités temporaire/programme/sortie, aucun NUL ajouté, alias, pointeurs invalides, propagation précise de `BT_*`, `BP_*`, `BL_*`, erreurs atomiques et scénario complet `30/10/20/LIST/20/LIST/NEW/LIST`. Les trois tests précédents restent inchangés, CTest enregistre quatre suites.

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --parallel
ctest --test-dir build --output-on-failure
cmake -S . -B build-asan -DCMAKE_BUILD_TYPE=Debug -DBP_SANITIZERS=ON
cmake --build build-asan --parallel
ctest --test-dir build-asan --output-on-failure
```

La CI GitHub `pull_request` exécute ces vérifications sur Linux standard et ASan/UBSan ; les résultats doivent être consultés sur la PR. Aucun exécuteur, REPL, écran CYD, UART ou gestion de fichier n'est ajouté.
