# J0.8 — Orchestration de session BASIC native, non bloquante

**État : accepté par Pilotage et intégré dans `main` le 24 octobre 2026** via [PR #8](https://github.com/Kharn27/ESP32-Locomotive-Basic/pull/8), merge squash `d21af73d8e03326ec9fdb10060350955c9886c45`.
Revue du diff réel et CI [#40081828507](https://github.com/Kharn27/ESP32-Locomotive-Basic/actions/runs/40081828507) : Linux C99 strict 6/6 et ASan/UBSan 6/6. J0.9 non démarré. Ce module n'est pas une émulation CPC/Z80
et n'accède à aucun périphérique. Il relie seulement les API J0.6 et J0.7.

## Découpage et choix d'architecture

Le nouveau composant `core/basic_session_runtime.h/.c` est une couche
d'orchestration indépendante du matériel :

- `basic_session` conserve *sans modification* la saisie, la tokenisation,
  les lignes numérotées, `LIST` et `NEW` ;
- `basic_executor` conserve la validation, le curseur d'offset et l'exécution
  atomique d'une seule ligne (`PRINT`, `GOTO`) ;
- `basic_program` reste le seul propriétaire logique des lignes stockées.
  Les données et buffers sont physiquement fournis par l'appelant.

Le `RUN` direct n'a volontairement **pas** été ajouté à
`bs_process_line` : son refus historique J0.6 reste vérifiable.
`bsr_submit` filtre seulement les commandes exactes `RUN` et `NEW`
(après suppression des espaces ASCII extérieurs, casse ASCII ignorée)
avant/après délégation à `bs_process_line`, sans dupliquer le tokenizer.

## API publique et cycle de vie

```c
typedef enum { BSR_IDLE = 0, BSR_RUNNING } BSRState;
typedef struct BasicSessionRuntime {
    BasicProgram *program;
    BasicExecutor executor;
    BSRState state;
} BasicSessionRuntime;

BSRResult bsr_init(BasicSessionRuntime *runtime, BasicProgram *program);
BSRResult bsr_submit(BasicSessionRuntime *runtime,
                     const uint8_t *source, size_t source_length,
                     uint8_t *temporary, size_t temporary_capacity,
                     uint8_t *output, size_t output_capacity,
                     size_t *written);
BSRResult bsr_step(BasicSessionRuntime *runtime,
                   uint8_t *output, size_t output_capacity, size_t *written);
BSRResult bsr_stop(BasicSessionRuntime *runtime);
```

1. Appelant : `bp_init` avec son stockage, puis `bsr_init`. Cette dernière
   vérifie le programme via `be_init` sur une instance locale temporaire,
   initialise la session en `BSR_IDLE` et n'altère **rien** si elle échoue.
2. Appelant : `bsr_submit` sur des lignes, `LIST`, `NEW` ou vide.
   Les lignes numérotées suivent exactement le contrat J0.6.
3. `RUN` direct exact : `be_init` valide le programme et repositionne
   l'exécuteur sur la première ligne ; la session devient `BSR_RUNNING`.
   `*written=0`. **Aucun appel `be_step` et aucun octet de sortie**.
   Un nouveau `RUN` pendant `RUNNING` recommence dès la première ligne.
4. L'application hôte appelle `bsr_step` à la cadence de son choix.
   Chaque invocation appelle `be_step` **au plus une fois**, traite au plus
   une ligne numérotée, puis retourne au code hôte. Une boucle
   `10 GOTO 10` ne provoque aucune boucle C interne.
5. Un pas atteignant la sentinelle fait retourner `BSR_END` et remet l'état
   à `BSR_IDLE`, **sans modifier le contenu de sortie, `*written` ni
   `executor.cursor`** durant ce pas. Un pas ultérieur sans RUN retourne
   `BSR_NOT_RUNNING` sans effet.
6. `bsr_stop` bascule vers `BSR_IDLE` sans effacer les lignes BASIC, y compris
   s'il est déjà inactif. Un prochain RUN repart de la première ligne.

Le statut `BSR_OK` d'un pas peut correspondre à une ligne sans sortie
(`GOTO`, ligne vide) ; seul `BSR_END` signifie la fin. Le buffer n'est ni
terminé par NUL, ni effacé. La sortie de `PRINT` est celle de J0.7.

## Discipline édition/exécution

| Requête pendant RUNNING | Règle J0.8 |
|---|---|
| Numéro de ligne reconnu par J0.6 (premier octet = chiffre ASCII) | `BSR_BUSY`, aucune mutation ni tokenisation |
| `LIST` | Autorisé ; curseur d'exécution inchangé |
| `NEW` | Appelle J0.6 ; passe à IDLE **seulement si BS_OK** |
| Ligne vide / espaces seulement | Sans effet ; `*written=0` |
| `RUN` | Réinitialisation explicite du curseur, même pendant exécution |
| `RUN 10`, autre direct non supporté | Diagnostic J0.6 conservé |
| `RUN:LIST` ou autre direct multiple | `BS_MULTIPLE_DIRECT` conservé |

Une saisie avec des espaces *devant* un numéro de ligne n'est pas une
édition valide dans la grammaire J0.6 : elle reste refusée par la session.
Les éditions via `bs_process_line` directement ou les mutations directes de
`BasicProgram` pendant RUNNING sont **interdites par contrat**. Il n'existe
pas de verrou concurrent ni de copie/snapshot automatique du programme.

## Diagnostics et garanties d'atomicité

`BSRResult` conserve trois champs : `BSRStatus status`,
`BSResult session` (les quatre valeurs `BS_ / BT_ / BP_ / BL_`) et
`BEStatus executor_status`. Les états de la couche :

| `status` | Interprétation |
|---|---|
| `BSR_OK` | Commande ou pas exécuté normalement |
| `BSR_END` | Fin naturelle, session passée à IDLE |
| `BSR_NOT_RUNNING` | Aucun programme actif |
| `BSR_BUSY` | Édition de ligne interdite pendant RUNNING |
| `BSR_INVALID_ARGUMENT` | Argument requis NULL, session non initialisée |
| `BSR_OVERLAP` | Zones mémoires interdites se recouvrent |
| `BSR_SESSION_ERROR` | Détail original dans `session`, sans perte |
| `BSR_EXECUTOR_ERROR` | Détail original dans `executor_status`, sans perte |

Pour `BSR_END`, `executor_status` conserve `BE_END`.
En l'absence d'erreur sous-jacente, les champs de détail valent
`BS_OK / BT_OK / BP_OK / BL_OK` et `BE_OK` respectivement, sauf fin naturelle. Les statuts
`BE_MISSING_TARGET`, `BE_NO_SPACE`, `BE_BAD_SEQUENCE`, etc. remontent
tels quels. **En cas d'erreur de `be_step`, le runtime reste RUNNING**, le
curseur, `*written` et la totalité de `output` ne sont pas modifiés.
L'appelant peut augmenter sa capacité de sortie et rappeler `bsr_step`
ou interrompre via `bsr_stop`. Une erreur logique persistante peut donc
être signalée à chaque pas ; aucune interruption automatique n'est cachée.

`bsr_submit` valide pointeurs et recouvrements avant d'agir ; les échecs
`BSR_BUSY`, syntaxe, tokenizer, stockage, listing ou `be_init`
n'altèrent pas l'état session, la sortie ou `*written`. Le buffer
temporaire peut changer si le tokenizer a commencé (contrat J0.6).
Sur NEW, l'arrêt n'est validé qu'après succès de `bs_process_line`.
Sur un RUN invalide, l'exécuteur en cours demeure intact.

## Préconditions RAM, durée et portabilité

- C99 strict ; aucun heap, VLA, état global mutable, thread, scheduler ni
  dépendance à Arduino/ESP-IDF.
- `BasicSessionRuntime` est public et instanciable sur pile/statique :
  un pointeur de programme, un `BasicExecutor` (pointeur + offset) et un
  `BSRState`. Taille réelle dépendante de l'ABI ; allocation dynamique = 0.
- L'appelant conserve valides les objets mémoire jusqu'à la fin d'utilisation.
  Pour `bsr_submit`, les sept régions (runtime, descripteur programme,
  **capacité entière** du stockage programme, source, **capacité entière**
  du tampon temporaire, **capacité entière** de sortie et `*written`)
  doivent être deux à deux distinctes. `bsr_step` vérifie les régions
  utiles runtime/programme/stockage/sortie/`*written`. Même de capacité
  zéro, les pointeurs obligatoires ne peuvent pas être NULL.
- Les recouvrements sont testés avec `uintptr_t` sur Linux et ESP32 ;
  sans `uintptr_t`, ils demeurent une précondition de l'appelant.
  Les étendues annoncées doivent vraiment appartenir à des objets valides.
- Aucun buffer supplémentaire proportionnel au programme ou à une ligne.
  La vérification des plages examine un nombre fixe de paires. Chaque
  pas ne peut exécuter qu'une ligne, même avec `GOTO` vers elle-même.
  Le coût d'une étape dépend de l'analyse/validation de cette ligne et
  du programme ; non d'un nombre de lignes exécutées en boucle interne.

## Vérifications

Une sixième suite `tests/test_basic_session_runtime.c` est enregistrée dans
CTest. Elle couvre le scénario entier saisie / LIST / RUN / 3 pas / END,
le deuxième RUN, les variantes de casse, programme vide, arrêt/reprise,
NEW et LIST pendant l'exécution, refus des éditions pendant RUNNING,
boucle de 1000 pas pilotée par l'appelant, cible GOTO absente, sortie trop
petite puis nouvel essai, diagnostics BS/BE, argumentation et recouvrements,
et préservation de l'état et des buffers lors des échecs.

Exécuter depuis la racine :

```sh
cmake -S . -B build -DBP_SANITIZERS=OFF
cmake --build build
ctest --test-dir build --output-on-failure
cmake -S . -B build-asan -DBP_SANITIZERS=ON
cmake --build build-asan
ctest --test-dir build-asan --output-on-failure
```

Le workflow existant s'exécute aussi sur les PR avec les deux configurations.

## Écarts au CPC

Il s'agit seulement de l'orchestration hôte. Les commandes `PRINT` et
`GOTO` restent limitées au sous-ensemble J0.7 ; ni `FOR/NEXT`, ni
variables, ni `RUN 10`, ni `CONT`, ni interruptions CPC, ni console UART,
ni rendu ILI9341, ni codes d'erreurs ROM historiques. La fin et l'arrêt sont
des résultats d'API C, pas une imitation de la boucle interactive CPC.

Références : **[C]** `basic.asm` expose le dispatch direct et `RUN`
dans les routines historiques ; **[D]** séparation native session/exécuteur
et pas borné par appel C, choix nouveau du projet ; **[V]** fidélité des
détails d'exécution et de présentation CPC à comparer plus tard.
