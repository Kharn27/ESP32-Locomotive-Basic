## Construction et execution

Depuis la racine du depot :

~~~sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug -DBP_SANITIZERS=OFF
cmake --build build --parallel
ctest --test-dir build --output-on-failure
./build/loco_basic_cli
~~~

Verifier egalement la configuration de diagnostic :

~~~sh
cmake -S . -B build-asan -DCMAKE_BUILD_TYPE=Debug -DBP_SANITIZERS=ON
cmake --build build-asan --parallel
ctest --test-dir build-asan --output-on-failure
~~~

Le projet impose C99 sans extensions et, sur GCC/Clang,
-Wall -Wextra -Wpedantic -Wconversion -Werror. Le workflow GitHub Actions
existant couvre les deux configurations sur chaque PR.

## Session type

Entrer les commandes ci-dessous dans le terminal (ou les rediriger depuis
un fichier). Les textes entre crochets sont des messages **de l'hote**,
envoyes sur stderr ; ils ne font pas partie de la sortie BASIC.

~~~text
10 PRINT "HELLO"
20 PRINT 42
LIST
RUN
:step
:step
:step
:quit
~~~

Sur **stdout**, les octets produits par le coeur sont exactement :

~~~text
10 PRINT "HELLO"
20 PRINT 42
HELLO
42
~~~

Sur **stderr**, on obtient les messages de service suivants
(sans prompt si stdin/stdout sont rediriges) :

~~~text
[cli] J0.9 host CLI (:help)
[cli] OK
[cli] OK
[cli] LIST
[cli] RUNNING
[cli] STEPPED 1
[cli] STEPPED 1
[cli] END
[cli] BYE
~~~

Sur un terminal interactif (stdin et stdout sont des TTY), un prompt
"basic> " est affiche sur stderr, avant chaque saisie. Le prompt
est absent en mode script afin de garder stdout exclusivement BASIC.

## Commandes et fonctionnement

- **BASIC** : lignes numerotees, suppression/reecriture de lignes,
  LIST, NEW et RUN dans le sous-ensemble J0.8. Les saisies sont
  transmises telles quelles a bsr_submit, sans nouveau tokenizer.
  Les regles historiques limitees de J0.6/J0.8 sont conservees
  (notamment : aucun espace initial devant un numero de ligne).
- **:help** : rappels des commandes (stderr).
- **:step** : exactement un appel au plus de bsr_step.
- **:step N** : au maximum N appels a bsr_step, avec N decimal
  entre 1 et 100 inclus. Rejet des valeurs nulles, superieures,
  negatives, non numeriques et des depassements ; aucune execution
  dans ces cas.
- **:stop** : appel a bsr_stop, preserve les lignes BASIC ;
  l'arret est idempotent.
- **:quit** : appel a bsr_stop, affiche BYE, puis quitte (code 0).
  Un EOF vide affiche EOF et arrete proprement le runtime.
- Les meta-commandes sont reservees au terminal, reconnaissables
  par leur deux-points initial (espaces ASCII exterieurs admis).
  Elles sont sensibles a la casse, contrairement aux commandes
  BASIC directes. Une meta-commande inconnue donne UNKNOWN_META
  sans etre transmise au coeur.
- RUN repositionne le curseur et demarre l'etat RUNNING, **sans**
  executer de ligne. :step N s'arrete a la premiere fin ou erreur,
  sans utiliser de boucle BASIC implicite. Un GOTO vers lui-meme
  ne bloque jamais le terminal au-dela du nombre demande.
- Une edition numerotee pendant RUNNING produit BSR_BUSY, mais
  LIST et NEW conservent le comportement defini en J0.8.

## Contrat de sortie et messages stables

stdout est reserve aux octets BASIC : LIST et PRINT, sans prefixe,
sans terminateur NUL ajoute. Seuls les octets couverts par
la valeur "written" du **dernier succes BSR_OK** sont emis avec
fwrite. Aucun octet precedent n'est reutilise sur BSR_END,
BSR_NOT_RUNNING ni sur une erreur. Les buffers de sortie ne
sont pas reinitialises arbitrairement.

stderr contient exclusivement les informations de service et erreurs
de l'hote. Le vocabulaire de service est fixe :

| Message stderr | Sens |
|---|---|
| [cli] J0.9 host CLI (:help) | Banniere initiale |
| [cli] OK | Saisie/edition/NEW/vide acceptee |
| [cli] LIST | Commande LIST acceptee (eventuellement vide) |
| [cli] RUNNING | RUN accepte, aucun pas execute |
| [cli] STEPPED N | N pas effectifs termines avec BSR_OK |
| [cli] END | Fin naturelle BSR_END et retour a IDLE |
| [cli] STOPPED | Arret explicite :stop |
| [cli] BYE | Fin sur :quit |
| [cli] EOF | Fin sur fermeture de stdin |
| [cli:error] INPUT_TOO_LONG | Ligne trop longue, integralement consommee et rejetee |
| [cli:error] INVALID_STEP (expected 1..100) | Argument de :step invalide |
| [cli:error] UNKNOWN_META | Meta-commande inconnue |
| [cli:error] INPUT_IO / OUTPUT_IO | Erreur fatale d'E/S (exit 1) |

Les retours d'API non BSR_OK sont signales ainsi sur une ligne stderr :

~~~text
[cli:error] BSR_EXECUTOR_ERROR BS_OK BT_OK BP_OK BL_OK BE_MISSING_TARGET
~~~

Le premier nom est le statut orchestration BSR ; suivent sans perte
les valeurs des champs BS, BT, BP, BL et BE. Ces identifiants sont
**des diagnostics du coeur C**, et non les codes/messages ROM CPC.
Pour BSR_END, le message distinct [cli] END suffit et aucun buffer
preserve par l'API n'est reemis. En cas d'erreur d'execution, le
runtime reste RUNNING (contrat J0.8) : l'utilisateur peut retenter
:step, consulter LIST, ou interrompre avec :stop.

## Capacites fixes

| Element | Capacite | Limite |
|---|---:|---|
| Programme binaire | 32 768 octets | Inclut la sentinelle finale du format BASIC |
| Ligne physique d'entree | 512 octets | Hors LF ; CR de CRLF compte avant suppression ; au-dela : rejet total et vidage de la ligne |
| Tampon temporaire de tokenisation | 2 048 octets | BT_NO_SPACE remonte en cas de depassement |
| Tampon de sortie (LIST / un pas) | 131 072 octets | BL_NO_SPACE / BE_NO_SPACE si insuffisant |
| :step N | 100 appels au maximum | Pas de RUN continu automatique |

Les tableaux et le runtime sont alloues dans une structure locale
sur la pile du processus. Le CLI n'utilise ni malloc/free, ni VLA,
ni thread, ni etat global mutable. Le programme, ses buffers,
le runtime et "written" occupent des regions disjointes comme
l'exigent les API J0.8. Les limites sont celles du CLI hote Linux,
**pas** un budget RAM valide sur ESP32 sans PSRAM.

Les entrees binaires (NUL) et autres constructions hors sous-ensemble
restent a la charge des validations existantes dans le coeur.
Les codes d'erreur core sont exposes sans reinterpretation.

## Validation hote / CI

La suite CTest supplementaire "host_cli" lance **l'executable reel**
avec des scripts stdin, recupere separément stdout et stderr,
verifie leur contenu *exact* et exige un exit code 0. Dix
scenarios automatises :

1. LIST ordonne + RUN et trois pas avec fin naturelle.
2. Boucle GOTO 10 bornee a 100 appels, arret puis NEW/LIST.
3. Reecriture de ligne, NEW et nouveau RUN.
4. :step 0, 101, argument non numerique, tres grand entier et
   execution hors session.
5. Commandes directes non supportees, commandes multiples et meta inconnue.
6. Entree surdimensionnee suivie de lignes valides, aucune pollution du programme.
7. EOF propre, erreur BE_MISSING_TARGET repetee sans reemission de PRINT.
8. BSR_BUSY sur edition pendant execution et LIST inchange.
9. Aide :help.
10. CRLF et derniere ligne sans LF.

Les six tests préexistants sont conservés. **Preuve de livraison acceptée sur le HEAD corrigé :**
[GitHub Actions #40083698694](https://github.com/Kharn27/ESP32-Locomotive-Basic/actions/runs/40083698694), le 24 octobre 2026 : **7/7 suites Linux standard** et **7/7 suites ASan/UBSan**, dont `host_cli`.
La revue Pilotage a exigé et validé `cmake_minimum_required(VERSION 3.13)` et les expansions explicites `${step1}` à la place de `@step1@`, sans modification fonctionnelle de la console ou du cœur. Chaque job compile avec les avertissements C99 stricts.
Ne pas confondre des tests de non-regression internes avec une
validation de fidelite sur un CPC reel.

## Frontiere CPC / hote

**CPC partiellement couvert** : syntaxe des lignes numerotees,
LIST/NEW/RUN et execution des sous-ensembles PRINT literal/entier,
GOTO et edition selon J0.3-J0.8.

**Adaptation Linux J0.9** : prompt TTY, :step / :stop / :help / :quit,
messages entre crochets, stdout/stderr et plafonds de buffers.

**Non implementes** : FOR/NEXT, variables, PRINT arbitraire,
mode graphique CPC, gestion console serie CYD, audio et stockage SD.
Il ne s'agit ni d'un emulateur Z80, ni d'une interface CPC definitive.
