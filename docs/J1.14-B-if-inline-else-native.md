# J1.14-B — IF INTEGER natif avec affectation directe et ELSE

**Mandat :** [#138](https://github.com/Kharn27/ESP32-Locomotive-Basic/issues/138). **Base initiale :** `main@c9c45bd38ffe70f889e71711fa082db6e3b23fc4`, fusion J1.14-A acceptée par Pilotage. **Périmètre strict** de J1.14-B, sans développement de J1.15, sans branche HW4 modifiée, et sans émulation.

## Architecture

Le tokenizer C99 accepte exclusivement un IF autonome :

```basic
IF A% [=|<>|<|<=|>|>= B%] THEN C%=81 [ELSE C%=42]
```

`A%` et `B%` sont des scalaires INTEGER explicites, et les affectations de branches portent une constante décimale entière non signée `0..255`, sans expressions. Le token `01` précédant `ELSE=97` vient du flux lexical CPC et **n'est pas un deux-points saisi**. Le `IF ... THEN <numéro>` préexistant reste séparé et non modifié. Les six explorations J1.14-A (ELSE isolé, branches vides, IF imbriqué, THEN GOTO, colon) sont **exclues**.

Le LIST traite les références explicites INTEGER et leurs caches opaques sans les interpréter comme séparateurs, décode `01 97` exclusivement dans cette branche, conserve les espaces du record et reconstruit les opérateurs signés. Un cache importé non nul ne peut être préservé par rétokenisation depuis une source textuelle : l'équivalence est alors lexicale, pas byte-exacte des caches ; les 24 originaux CPC capturés contiennent les caches de référence tels qu'archivés.

L'exécuteur décode les **deux** affectations sans aucune mutation ni consultation du store pour la branche non prise, puis prépare uniquement l'affectation choisie. La convention historique à deux passes `be_step` effectue le prévol de capacité, le contrôle de buffer et la validation complète avant `bvs_assign`. Un IF faux sans ELSE laisse le store inchangé et continue à la ligne suivante. Les opérandes de condition sont comparés comme `int16_t` signés sans extension à REAL5/STRING ni heap par pas.

## Référence externe post-implémentation

`tools/j1_14_b_native_verify.py` lit les **24 captures originales, immuables** de `tests/fixtures/cpc6128/j1_14_if_inline_else/`. Manifeste SHA256 externe : `dc1b30dee67d7bd9c9e5ac2db17bdb84730d48d41fec8d64924a1d2d4c6e0ec1`. L'archive a été produite par Caprice32/ROM CPC6128 indépendant (run GHCR 40743423595) et vérifiée par réacquisition ; aucun octet n'est déduit du code C99.

Pour chaque cas, la transcription hôte **en mémoire seulement** transforme strictement la ligne 40 `PRINT #8,C%` en `PRINT C%`. Puis :
1. comparaison de **l'enregistrement ligne 30 entier** CPC ↔ C99 : `MATCH_EXACT_RECORD_30` ;
2. `LIST` hôte, retokenisation, seconde comparaison ligne 30 ;
3. exécution hôte de l'IF et comparaison de la valeur numérique C% `81` ou `42` à la trace CPC : `MATCH_SEMANTIC_BRANCH`.

Les flux imprimante CPC et stdout Linux **ne sont pas égaux octet à octet** (`CPC_PRINTER_VS_HOST_STDOUT`), et les images BASIC globales diffèrent notamment pour la ligne 40. Les 24 classifications originales `UNSUPPORTED` pré-B restent inchangées. Le script vérifie également les SHA originaux, les deux acquisitions et les témoins `ERR/ERL`.
