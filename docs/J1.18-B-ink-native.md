## Contrat d'événements vidéo portable

`BEVideoEvent` conserve **dans le même ordre** les champs historiques `type`, `pen`, `print_offset` ; `BE_VIDEO_SET_TEXT_PEN=1` ne change pas. L'évolution ajoute `BE_VIDEO_SET_INK=2` et deux champs finaux `uint8_t ink` et `uint8_t colour`. Pour un INK : `pen=0`, `ink=p`, `colour=c`, `print_offset` = nombre de bytes PRINT déjà produits dans cette étape. Pour un PEN historique : `ink=colour=0`. **PEN est un indice logique texte, ink est l'indice logique de palette et colour un code couleur CPC** ; aucun n'est un indice pixel MODE1 ou un triplet RGB.

Le champ `print_offset` définit un ordre **intra-ligne** : `PRINT "A":PEN 3:INK 1,26:PRINT "B"` publie les octets `41 0A 42 0A` et deux événements à offsets 2 puis 2, de types PEN puis INK. Chaque étape rend les événements **exactement une fois** en cas de succès. L'appel historique `be_step` / `bsr_step` reste présent et doit retourner `BE_EVENT_RECEIVER_REQUIRED` si INK est atteint sans récepteur ; ni curseur, ni événement, ni sortie ne changent. Pas de perte silencieuse.

La validation en deux passes (préflight puis écriture/commit) couvre les capacités PRINT et événements, la source, les tokens importés, l'état, les overlaps et les arguments : les échecs sont atomiques. L'API ne réalise **aucun rendu**. Attention à la sémantique CPC mesurée dans J1.18-A : une modification de palette peut **recolorer les pixels déjà présents** sur écran sans nouveau PRINT. Cette obligation est transmise à l'intégrateur futur, pas implémentée ici.

### ABI et hardware indépendant

L'ordre et les offsets des champs initiaux restent inchangés ; les nouveaux champs sont **ajoutés à la fin** pour préserver aussi les initialiseurs C99 positionnels historiques. Dimensionnement attendu sur ABI GCC/Clang utilisées (à contrôler dans CI, avec `sizeof` et `offsetof` réels) :

| ABI | Ancien `sizeof(BEVideoEvent)` | Nouveau attendu | Surcoût par événement |
|---|---:|---:|---:|
| Linux 64 bits, `size_t=8` | 16 | 24 | +8 octets |
| Xtensa ESP32 32 bits, `size_t=4` | 12 | 16 | +4 octets |

Pour un tableau caller-owned de trois éléments côté firmware, **surcoût attendu 12 octets** ; aucun événement n'est intégré durablement dans `BasicExecutor` ou `BasicSessionRuntime`. Tout récepteur de `BE_VIDEO_SET_INK` doit être ajouté et validé dans une mission matérielle *ultérieure* ; **HW4-PEN-A #188 / PR #190 reste indépendant**. Le format évoluant, le Pilotage doit coordonner les merges/rebuilds hardware, sans greffe INK anticipée.
