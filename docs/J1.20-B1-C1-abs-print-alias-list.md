## Incompatibilité à arbitrer par Pilotage : RAM strictement identique

Cette correction règle l'échec de LIST **réentrant** sans modifier la
représentation des lignes CPC acceptées, mais **ne garantit pas** la RAM
strictement identique pour les quatre formes compactes de l'alias \`?\`.

Constat reproductible à partir du tokenizer et du listing du même HEAD :

| Opération | Octets de corps (début) |
| --- | --- |
| Tokenizer \`?ABS(1)\` | \`BF FF 00 28 0F 29\` |
| LIST de cette ligne (corrigé) | \`PRINT ABS(1)\` |
| Retokenizer \`PRINT ABS(1)\` | \`BF 20 FF 00 28 0F 29\` |

L'espace \`20\` est indispensable pour que le préfixe \`PRINT\` soit reconnu
comme mot-clé à la re-saisie. Les 16 sources historiques \`PRINT ABS(...)\`
disposent déjà de cet espace dans les flux tokenisés. Supprimer cet espace
à l'entrée du tokenizer modifierait leurs RAM CPC scellées ; conserver
\`PRINTABS(...)\` rendrait LIST non rééditable. Afficher \`?ABS(...)\`
préserverait les octets, mais renoncerait à la forme canonique
\`PRINT ABS(...)\` demandée pour LIST.

**Ne pas revendiquer \`ROUND_TRIP_EXACT_RAM\` sur l'alias compact.**
La suite vérifie le delta d'un octet et l'équivalence du contenu tokenisé
après ce séparateur. Elle exige **RAM strictement identique** pour les
quatre sources déjà espacées (\`? ABS(1)\`, \`PRINT ABS(1)\`,
\`PRINT  ABS(1)\`, \`PRINT #8,ABS(1)\`).

Pilotage doit arbitrer explicitement entre :
1. accepter le **round-trip sémantique** et le séparateur ajouté en RAM,
   en maintenant les 16/16 RAM CPC historiques exactes (option compatible
   avec ce correctif minimal) ;
2. changer l'exigence de représentation LIST ou le périmètre tokenizer
   après nouveau mandat ; en l'état, aucune de ces variantes n'est implémentée.
