## Contrat de prévisualisation / commit

Les fonctions `be_preview_step_events` et `bsr_preview_step_events` reçoivent des **buffers de préparation propres à l'appelant**, avec les mêmes règles de disjonction et validité des régions que l'exécution normale.

- `BE_OK` / `BSR_OK` : seuls `output[0..*written)`, `events[0..*event_written)` et leurs deux compteurs sont écrits. Le reste des buffers conserve ses canaris. **Aucune mutation** du programme, état RUN, curseur, piles, variables INTEGER, STRING, REAL5, entrées ni arena.
- `BE_END` / `BSR_END`, ou tout refus : aucun tampon, compteur ni état BASIC n'est modifié. Le `BE_END` de preview observe uniquement la sentinelle de fin ; le commit normal de `BSR_END` ramène BSR à IDLE.
- `be_step` et `bsr_step` sans récepteur continuent à refuser un `CLS` atteint avec `BE_EVENT_RECEIVER_REQUIRED`, **sans mutation**. Avec un tableau d'événements de capacité 0 ou 1 pour `CLS:CLS`, refus atomique avant écriture (`BE_EVENT_RECEIVER_REQUIRED` si pas de récepteur ; `BE_NO_EVENT_SPACE` sinon).
- **Cohérence** : pour l'état BASIC et les entrées empruntées *identiques* entre les deux appels, un commit immédiat doit générer les **mêmes octets PRINT** et les **mêmes événements typés/offsets**, puis modifier les états BASIC seulement après validation. Une preview ne bloque pas la concurrence et ne réserve aucun pas. Si source, store, curseur, capacité ou buffers évoluent entre preview et commit, le consommateur doit prévisualiser de nouveau.
- **Frontière B2b** : le futur scheduler, sous mandat séparé, sera responsable du pipeline `preview BASIC → preflight vidéo → commit BASIC → comparaison des sorties et événements → replay vidéo`. Toute divergence après le commit doit provoquer un **fail-stop sans replay** ; aucune garantie de rollback post-commit LCD n'est avancée par B2a. B2a n'émet ni pixels ni requête de rendu et ne modifie pas le scheduler.
