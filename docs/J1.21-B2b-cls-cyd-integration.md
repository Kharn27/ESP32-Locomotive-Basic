## Architecture et invariant

Pour chaque instruction (pas numéroté), le **même BSR réel** exécute :

1. `bsr_preview_step_events` dans les tableaux propres au scheduler ;
   aucun changement du curseur, piles GOSUB/FOR, variables, programme, compteurs
   vidéo ou sorties publiques.
2. `hw4_pen_preflight` : préflight **pur** sur événement(s) et PRINT, couverture
   globale du pas, refus INK avant toute écriture, contrôle MODE1 40×25,
   PAPER/PEN/palette, offsets croissants, validité des événements CLS.
3. `bsr_step_events` : commit BASIC unique dans les tampons publics.
4. Comparaison sur les octets PRINT, taille, événements, et champs typés,
   **avant** le premier pixel.
5. `hw4_pen_replay` : séquence strictement ordonnée à chaque `print_offset`
   des PRINT, PEN et CLEAR_TEXT, sans seconde VRAM.

Un préflight refusé retourne `HW4_RUN_DISPLAY_PREFLIGHT_FAILED` :
**zéro commit BASIC pour le pas courant**, sorties/compteurs publics et pixels
inchangés. Les pas déjà réussis dans un quantum restent naturellement validés.
`last_result` et statut du pilote indiquent le défaut ; les seules écritures
d'essai concernent le staging privé. Le `BSR_END` non committant est suivi du
commit `BSR_END` pour retrouver `BSR_IDLE`. Les erreurs BSR prévisualisées
préservent la provenance et les buffers publics.

La divergence preview/commit échoue sans replay sous
`HW4_RUN_DISPLAY_COMMIT_MISMATCH` : **pas de promesse de rollback** BASIC.
Le replay échoué retourne `HW4_RUN_DISPLAY_REPLAY_FAILED` et interrompt le RUN :
un pas BASIC déjà committé est compté, un pixel partiel n'est pas annulé.
Dans ces deux cas, aucune instruction suivante n'est exécutée.
`BREAK` n'interrompt pas le replay du pas achevé ; `YIELD` ne stoppe pas BSR.

CLS ne réinitialise ni MODE, ni PEN, ni PAPER, ni INK[], ni bordure. Il
remplit les 16000 octets de l'**unique VRAM** MODE1 avec le motif
`PAPER * 0x55`, invalide les 1000 cellules sémantiques (dont les 125 octets
de validité), marque les 25 bandes comme sales et remet le curseur texte
à (0,0) avec visibilité préservée. Les compteurs du sink restent monotones.
`!CLS` reste l'opération distincte du service UART qui réinitialise
la présentation et restaure les encres propres au CONSOLE.

## Mémoire / financement sans allocation

Le scheduler CONSOLE `s_run_scheduler` est statique, et ses scratchs sont
**caller-owned**, pas sur la pile d'un callback ni sur le heap.

| Allocation ajoutée | Budget C99 calculable |
|---|---:|
| `preview_output[4096]` | 4096 octets |
| `preview_events[8]` | `8 × sizeof(BEVideoEvent)` |
| deux `size_t` de staging | `2 × sizeof(size_t)` |
| **Total nouveau staging** | `4096 + 8*sizeof(BEVideoEvent) + 2*sizeof(size_t)` |

Sur une cible ESP32 32 bits, si `sizeof(BEVideoEvent)==16` (à confirmer
par compilation), staging = **4232 octets** ; aucun double framebuffer
de 16000 octets, aucune duplication du magasin BASIC. Le **Δ DRAM réel**
doit être établi par `idf.py size` (et non supposé égal à la taille des
champs à cause des sections et alignements). La pile principale configurée
reste 6144 octets. La capacité des sorties publiques reste 4096,
événements CONSOLE 3 ; scheduler accepte jusqu'à 8 événements/4096 octets.

**Base post-B2a exacte** : [CI Xtensa main #41443115971](https://github.com/Kharn27/ESP32-Locomotive-Basic/actions/runs/41443115971).

## Preuves C99 / journal RED → GREEN

- **RED, défaut de la base :** `integration/hw4_run_scheduler.c` à
  `748c49e` appelle `bsr_step_events` *avant* `receiver->preflight`;
  pour `10 PRINT "A":CLS:PRINT "B"` rejeté, la mutation du cursor
  précède le rejet. Le test snapshot B2b est spécifiquement construit
  pour échouer contre cette implémentation. **RED source-inspecté ;
  exécution historique RED non revendiquée tant qu'un run dédié n'est pas publié.**
- **GREEN à vérifier sur Actions** :
  `j1_21_b2b_cls_transactional_mode1` avec BSR réel et
  snapshots byte-exact du programme, store/arena/entrées, executor/piles,
  output/events/counts et VRAM + état vidéo. Les scénarios incluent
  PRINT:CLS:PRINT refusé, A%/A$ + CLS (si grammaire B1 acceptée),
  INK précédé de PEN/PRINT et CLS, CLS:CLS, PRINT/CLS/PRINT ordonné,
  PAPER courant, palette, sémantique E2, événement malformé,
  état vidéo incompatible, replay fail-stop, divergence provoquée.
- Les suites historiques `hw4_run_break_a_cooperative_bsr`,
  `hw4_run_break_b_uart_console_contract`, PEN, INK, !CLS,
  CI-C99 4 cellules GCC/Clang OFF/ON ASan/UBSan, ARCH, CPC permanent
  et indépendant, OPT3 et Xtensa 3/3 doivent toutes rester vertes.
  `SKIPPED` ne vaut pas `PASS`.

## Protocole physique PO **après gates vertes**

Ne pas flasher avant **autorisation de test du Pilotage** et CI-ARCH verte
sur le SHA final. CYD ESP32-2432S028R sans PSRAM, ILI9341 320×240, UART
115200. Sur le poste Linux muni d'ESP-IDF **v5.5.6** :

```bash
git fetch origin
git switch feat/j1-21-b2b-cls-mode1-transactional
git pull --ff-only
git rev-parse HEAD                # doit égaler le SHA complet de la PR
cd firmware/esp32_display_probe
idf.py -B build-u1-console -DLOCO_CYD_PROFILE=CONSOLE build
idf.py -B build-u1-console -p /dev/ttyUSB0 flash monitor
```

Le workflow VS Code habituel Build / Flash / Monitor avec profil CONSOLE est
également permis, **à condition de vérifier le SHA embarqué affiché**.
Aucune modification du partitionnement, pas de `fullclean`, ni de
nouveau projet. Sauvegarder **tout le log UART** depuis boot (dont version SHA,
diagnostics `BASIC_SUBMIT`, `RUN_TERMINAL`, `HW4-PEN-A`, HEAP/DMA)
et photographier le TFT après les étapes 2 et 3.

Scénario, saisir chaque commande suivie de Entrée dans le terminal série :

```basic
NEW
10 PRINT "AVANT"
20 CLS
30 PRINT "APRES"
40 END
LIST
RUN
LIST
```

**Attendu :** avant RUN, LIST montre les quatre lignes intactes.
Pendant RUN, AVANT est effacé par CLS ; **APRES** apparaît à l'origine
texte MODE1, puis Ready revient normalement. LIST final conserve les
quatre lignes. Pas d'ERROR, pas de `VIDEO_REJECT` ou de fault DMA.
Photographier APRES et fournir UART complet.

Répéter séparément après `NEW` :

```basic
10 CLS:CLS
20 END
RUN
```

Attendu : pas de clignotement/palette réinitialisée, deux CLS successifs,
Ready. Puis :

```basic
NEW
10 PRINT "A":CLS:PRINT "B"
20 END
RUN
```

Attendu : **B visible, A effacé**, Ready, aucun fragment A résiduel.
Tester `10 PEN 3:PRINT "VERT":CLS:PRINT "OK"` (après NEW) :
OK dans le PEN 3 existant, INK0 bleu/INK1 jaune/INK2 rouge/INK3 vert
inchangées. Faire `!CLS` : opération de service distincte, écran
remis au boot/Ready sans perdre le programme ; ensuite `LIST`.

Test de rejet sans effet : après `NEW`, enregistrer
`10 PRINT "NON":INK 1,26:CLS` et `20 END`, puis `RUN`.
Attendu : diagnostic VIDEO_REJECT preflight, **NON jamais imprimé** par
ce pas, aucun CLS effectif et pas de pas suivant ; Ready/diagnostic
hôte selon politique CONSOLE, programme toujours listable.
Attention : le diagnostic hôte lui-même s'affiche **après** le rejet,
ce qui ne doit pas être confondu avec un effet vidéo du pas rejeté.

Régression BREAK/YIELD : `NEW`, `10 PRINT "BOUCLE"`,
`20 GOTO 10`, `RUN`, puis `!BREAK` et Entrée : RUN s'interrompt
sans reboot, Ready unique ; aucune ligne BASIC suivante ni second ERROR.
Faire `NEW` / `LIST` et confirmer vide.

**PASS uniquement si** photo TFT + log UART corroborent version/sha exact,
ordre CLS, conservation palette/programme, Ready, rejet, !CLS et BREAK.
Relever `heap_free`, `largest_block`, pile/high-water, DRAM/IRAM
si le firmware ou `idf.py size` les expose ; ne pas inventer des métriques.
Signaler explicitement tout cas impossible à exécuter. Pas de résultat PO
anticipé : statut `ON_DEVICE_UNVERIFIED` jusqu'à retour.
