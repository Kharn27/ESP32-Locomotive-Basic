## API publique et frontière explicite C2

`BSRResult bsr_prepare_direct_events(BasicSessionRuntime *runtime, const uint8_t *source, size_t source_length, uint8_t *output, size_t output_capacity, size_t *written, BEVideoEvent *events, size_t event_capacity, size_t *event_written)`.

- **C1 ne modifie pas le contrat existant de `bsr_submit`** : `RUN`, `LIST`, `NEW` et leurs diagnostics gardent leurs chemins et comportements. Tant que le firmware n'utilise pas cette nouvelle API, `bsr_submit("CLS")` reste `BSR_SESSION_ERROR / BS_UNSUPPORTED_DIRECT`. Ainsi **aucun CLS direct ne s'affiche sur CYD dans C1** ; seul C2 est autorisé à brancher le prompt.
- La nouvelle API **classe elle-même** les octets du direct, sans tokenisation/détokenisation externe, sans insertion de `10 CLS`, sans `RUN` caché, aucune variable, pile/cursor/état programme ni mutation de la palette. Le futur firmware C2 n'aura **pas à reparcourir ou deviner la syntaxe** pour obtenir l'événement.
- En `BSR_IDLE`, `CLS`, `cls`, `cLs` et espaces ASCII **extérieurs** : `BSR_OK`, zéro PRINT (`*written=0` sans écrire `output`), exactement un `BEVideoEvent` de type `BE_VIDEO_CLEAR_TEXT=3`, `print_offset=0`, tous champs réservés à zéro, `*event_written=1`. La source CPC encodée correspond au **token `8A`**, vérifié via le tokenizer B1 indépendamment du chemin direct ; l'événement n'est pas un octet PRINT.
- Les buffers et compteurs de l'appelant, de capacité explicite, doivent être **disjoints** entre eux et de l'état BSR, du programme entier, source, magasin/entrées/arena. Sur rejet, **aucune** mutation du moindre buffer/compteur public ni du BASIC. Source immutable ; aucun pointeur conservé ; aucun malloc ni variable globale.
- `events==NULL` avec capacité zéro : `BSR_EXECUTOR_ERROR / BE_EVENT_RECEIVER_REQUIRED` ; événement fourni avec capacité zéro : `BE_NO_EVENT_SPACE`. `event_capacity=1` suffit ; sorties `output_capacity=0` acceptées pour CLS. Capacité débordante ou pointeur non conforme : `BSR_INVALID_ARGUMENT` ; chevauchement : `BSR_OVERLAP`.
- Direct reconnu en `BSR_RUNNING` : `BSR_BUSY`, **sans interruption** de RUN ni mutation. `CLSX`, `CLS #1`, `PRINT "X"`, `RUN` via cette API : `BSR_SESSION_ERROR / BS_UNSUPPORTED_DIRECT`. `CLS:CLS` et autres deux-points directs non quotés : `BS_MULTIPLE_DIRECT`. NUL/CR/LF intégrés : `BS_MALFORMED_INPUT`. Aucun diagnostic CPC numérique inventé.

**Frontière C2 :** côté HW4 seulement après fusion C1, implémenter `C1 prepare → préflight vidéo → replay`, avec staging/counters séparés et `Ready` une seule fois ; pas de commit BASIC requis en C1. Ne pas confondre `!CLS` (service hôte). C1 n'émet ni pixels ni `Ready`.

## RED / GREEN reproductible et limites

Le test C99 `tests/test_j1_21_c1_direct_cls.c` contient un **témoin RED historique** : `bsr_submit("CLS")` échoue selon le contrat ancien `BS_UNSUPPORTED_DIRECT` ; la **nouvelle API C1** doit réussir le même texte en préparant l'événement unique, sans changer les octets BASIC. Le test laisse le rejet historique inchangé afin de préserver C2 et les diagnostics. Une véritable campagne CI exécutée sur un commit RED sans implémentation doit être distinguée d'un simple témoin différentiel ; **aucune CI RED historique isolée revendiquée**.

Vérifications C99 du contrat : casse/espaces, token 8A, émission typée sans PRINT, canaris au-delà de l'événement, répétitions, copie exacte du programme y compris capacité, store INTEGER/STRING/REAL5, arena, piles/cursor, état BSR, RUNNING refusé, tailles 0/1, null/overlaps, syntaxe non permise, diagnostics et LIST/RUN/NEW hérités. `bp_validate` et `bvs_validate` restent utilisés sur les structures empruntées ; aucune ligne provisoire.

**Qualification :** `CPC_DIRECT_ORACLE_OBSERVED` pour **acceptation de CLS direct et programme LIST conservé**, **PAS** `MATCH_EXACT` de l'écran, de l'événement typé interne, du curseur, de la casse mixte, des couleurs ni du Ready : les captures CPC ne valident pas ces détails du C99/CYD. `D_WINDOW`, `D_PAPER`, `D_INK`, `D_HASH*` ne sont **pas implémentés** en C1.
