## Chaîne de provenance

Caprice32 épinglé au commit `8c778bf072a06fb7c23b9cccd179041db7f79a52` ; image immuable `ghcr.io/kharn27/esp32-locomotive-basic-caprice32@sha256:7c2ac82df92a2df5c7305cc0bd70dc95124249fb46b2d893449f3d48395ced8c` ; ROM système CPC6128 SHA-256 `31c3668c67bea027dab698ece233c9434d9324f9ba7dac84db58f400b6689562`. Contrôles réels de l'outil `j1_18_a_ink_evidence.py` réemployés sans modifier cet oracle.

L'archive est acquise par deux **sessions CPC propres** `original` et `repeat` pour chaque programme (deux processus supplémentaires distincts pour la voie LIST et RUN de chaque session). Les sources d'entrée sont figées séparément dans `tests/oracles/inputs/j1_25_a/<CASE>.bas`, et vérifiées octet par octet. `MODE 1`, `NEW`, saisie originale, `LIST` écran, `LIST #8`, capture SNA *temporaire* puis extraction du programme RAM à l'aide du parseur historique ; **la SNA ni les ROM ne sont archivées**. Un second démarrage CPC propre exécute `RUN` ; `PRINT #8` donne la sortie sans la confondre avec les messages écran, et les sondes directes `ERR`/`ERL` sont ajoutées **après** le RUN, derrière le séparateur explicite `J125_DIAG_BEGIN`. Le test vérifie les bytes tokenisés, les lignes, LIST avant/après, le flux imprimante, les captures écran et les métadonnées d'origine.

**Canaux distincts :** la sortie imprimante ne prouve pas le texte d'erreur ou Ready dessiné à l'écran. Une lecture manuelle des PNG et de leur contexte est nécessaire avant d'annoncer un diagnostic textuel CPC. Le test ne fait aucune traduction `PRINT #8` vers le `PRINT` natif.

## Références ROM statiques (sans extrapolation comportementale)

Dans le désassemblage historique `basic.asm` fourni : table des mots-clés `DATA = 0x8C` (entrée e549), `READ = 0xC3` et `RESTORE = 0xC7` (entrée e4ff). Routines commentées `DATA = E9A3`, `READ = DCDA`, `RESTORE = DCC8`. **ROM_STATIC_ATTESTED** : ces correspondances ne prédisent ni avance du pointeur DATA, ni comportement des deux-points, ni diagnostics. Les octets réels RAM doivent être confirmés séparément par acquisition.

## Protocoles de reproduction et scellement

1. Depuis le SHA d'acquisition exact, exécuter la tâche GitHub Actions `J1.25-A independent DATA READ RESTORE CPC oracle` dans le conteneur GHCR épinglé. Vérifier la ROM et Caprice32, exiger le même HEAD branch PR et base ancestrale ; vérifier l'absence de diff de production.
2. `python3 tools/j1_25_a_data_read_restore_evidence.py --check --self-test` : source seule ; **pas** une acquisition.
3. `python3 tools/j1_25_a_data_read_restore_evidence.py --acquire tests/oracles/caprice32 --output <NOUVEAU_DOSSIER> --head <SHA_COMPLET>` (répertoire vide inexistant). L'action GitHub publie les archives brutes sur la branche *après* preuve de provenance, avant tout jugement de résultat.
4. Sceller `manifest.json` avec son SHA-256 issu du journal/artefact **du premier run GitHub**, puis enregistrer le **SHA exact d'acquisition indépendant** dans les constantes `EXTERNAL_MANIFEST_SHA256` et `EXTERNAL_ACQUISITION_HEAD` ; ne jamais les calculer depuis le candidat à vérifier.
5. `python3 tools/j1_25_a_data_read_restore_evidence.py --verify tests/fixtures/cpc6128/j1_25_a_data_read_restore --permanent --self-test` : certificat hors candidat, **≥8 falsifications rejetées** ; la CI CPC-PERMANENT échoue fermée si l'archive existe sans ancrages externes.

Les empreintes finales, l'identifiant GitHub Actions, le SHA d'acquisition, la concordance original/repeat, les éventuels désaccords et les classifications `OBSERVED/INCONCLUSIVE/UNVERIFIED` doivent être **remplis après** acquisition et non supposés à partir de la ROM.

## Limites et barrières

- Les programmes `DATA_EXHAUSTED` et `TYPE_MISMATCH` visent des diagnostics réels, mais **aucun libellé, ERR ni ERL ne doit être inventé** ; capter et interpréter l'image écran.
- Une éventuelle impossibilité de tokeniser un cas (notamment `DATA_COLON`) ou de répéter une acquisition est un échec/incident à remonter au Pilotage, **pas** une autorisation de réécrire silencieusement le cas.
- Aucun champ `C99_NATIVE_SUPPORTED` ni `ON_DEVICE_VERIFIED` ne découle de cette phase. **`ON_DEVICE_NOT_APPLICABLE_A`** ; pas de test CYD, pas de B1/B2.
