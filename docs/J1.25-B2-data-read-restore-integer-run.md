## Contrat implémenté

- CORE C99 `DATA` : les entiers ASCII décimaux positifs attestés, jusqu'à deux éléments par ligne, y compris `DATA 1:PRINT #8,"BEFORE"`. DATA n'avance pas le curseur READ.
- `READ A%` et `READ A%,B%` : références B1 explicites, types INTEGER uniquement, stores existants, deux affectations maximum par instruction. Curseur conservé comme **offset d'enregistrement + offset d'élément** dans le dernier slot WHILE existant lorsque aucune frame WHILE n'est active. **Erratum C1** : les instructions DATA/READ/RESTORE *non atteintes* ne bloquent plus WHILE ; seules les combinaisons réellement atteintes sont refusées afin de protéger le curseur et les huit frames. Voir [rapport C1](J1.25-B2-C1-iram-while-report.md). Ce partage maintient l'ABI publique préexistante et les 8 frames WHILE. Le balayage des DATA suit l'ordre des lignes stockées même si GOTO saute les lignes DATA à l'exécution.
- `RESTORE` remet au premier élément, `RESTORE 100` positionne au DATA en ligne 100. Pas de RESTORE arbitraire ni de STRING/REAL5.
- `PRINT #8,A%` / `B%` passe par le **canal PRINT CORE déjà existant**, avec le formateur INTEGER CPC existant. Aucun appareil imprimante, HAL ou firmware nouveau.
- `READ` prévalide **toutes** ses entrées, références et capacités avant toute mutation. La prévisualisation `be_preview_step_events` ne modifie pas le curseur ni les variables. RUN, STOP, NEW et fin de session invalident le curseur ; NEW réinitialise aussi le store selon l'API antérieure.
- `BE_DATA_EXHAUSTED` est **une cause interne native** et non `ERR=4`. Une étape READ échouée laisse intacts exécuteur, curseur, store, output/counters et programme. Les étapes antérieures réussies (par exemple valeur 1 imprimée) ne sont pas rétroactivement annulées.

4. Refaire avec `10 DATA 6,7`, `20 READ A%`, `30 PRINT A%`, `40 RESTORE`, `50 READ B%`, `60 PRINT B%`, `70 END`, `RUN`. Attendu : 6 puis 6, sans blocage ou corruption d'affichage. Recommencer via NEW pour éviter des lignes résiduelles.
