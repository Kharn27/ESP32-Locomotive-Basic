## Désassemblage et distinction unaire / binaire

Dans `basic.asm` 1.1, `D059` contient l'entrée `F5` qui dirige un moins **unaire** vers `D01D`; les routines `CF62–CFC5` et `D033` montrent que l'interprétation dépend du contexte d'expression. `F5` est également le token à rechercher **après A%** dans `B%=A%-n` ; il ne faut pas inventer un token « moins binaire » distinct. Le traitement unaire de `-32768` déjà authentifié est `F5 1F 00 00 00 00 90`, à distinguer du signe situé dans la seconde ligne.

Attentes indépendantes pour le suffixe de la ligne 20, avant le terminateur `00` : `F5 11` pour les cas à `-3`, `F5 0E` pour `-0`, `F5 0F` pour `-1`, `F5 19 FF` pour `-255`. Les tokens `0E..18` codent directement les petites constantes décimales. Ces signatures sont vérifiées contre la RAM CPC réellement extraite, **pas produites par le tokeniseur C99**.

2. Une session CPC 6128/128K BASIC 1.1 par cas : saisie ASCII exacte, `LIST` à l'écran, capture `list.png`, snapshot SNA **temporaire avant RUN**, extraction des seuls enregistrements tokenisés `program.bin` et destruction du SNA. Aucun ROM ni SNA archivé.
3. Une **seconde session indépendante** par cas : nouvelle saisie, `RUN`, capture écran `run.png` avant sondes en mode direct. Les instructions `PRINT #8,ERR` et `PRINT #8,B%` produisent `printer.dat` avec résultats/diagnostics chiffrés éventuellement exploitables ; ce n'est **pas** l'écran en octets.
4. `basic_program_image_cli` et `loco_basic_cli` C99 inchangés : image `MATCH_EXACT`, `DIFF` ou `UNSUPPORTED`; diagnostic et nombres natifs séparés des canaux CPC. Une concordance numérique après normalisation des fins de ligne serait au plus une `MATCH_PRESENTATION`, pas une égalité brute inter-transports.
5. Archive `tests/fixtures/cpc6128/j1_integer_subtraction/` : tous les fichiers bruts avec SHA-256, `manifest.json`, `seal.json` **PENDING_PILOTAGE**, provenance Git (SHA réellement checkouté = SHA événement), capture originale GitHub Actions + contrôle d'absence des fichiers interdits. Le validateur `tools/j1_3_subtraction_verify.py` applique dix falsifications contrôlées et un test négatif du SHA de checkout. La première acquisition est archivée via commit non forcé avec garde contre l'avancement concurrent de la branche ; une seconde compare octet pour octet les images et flux imprimante obtenus.

## Matrice d'observation à compléter avec l'archive

Pour chacun des six cas, contrôler sur preuves : SHA256 `program.bin`, suffixes de tokens des lignes 10 et 20, LIST (preuve visuelle), RUN (preuve visuelle), `ERR`, `B%` mesurés sur imprimante, `native_status`, `native_number`, catégorie image, concordance numérique seulement si justifiée. **Ne remplir cette matrice qu'après acquisition et lecture des artefacts.** Citer le run, l'ID et le SHA de l'artefact original, puis les liens Linux C99 OFF/ON, GHCR et Xtensa du HEAD final.

## Hypothèses ouvertes et proposition J1.3-B — interdit pour l'instant

La branche future, **si Pilotage autorise J1.3-B après revue**, pourrait implémenter uniquement une affectation INTEGER autonome `B%=A%-n` avec `0..255`, sans évaluateur général ni REAL5 supplémentaire. Observer d'abord le token `F5`, la limite `-32768`, l'atomicité et l'éventuel diagnostic du CPC au cas NMIN_M1. Le traitement exact du dépassement reste **non spécifié** avant preuve.

Les quatre B1 historiques autrefois `UNSUPPORTED`, les 18 comparaisons LIST/RUN historiques `UNVERIFIED` et l'absence de compatibilité CPC générale sont conservés.
